## Abstract

This HIP proposes replacing Helm's current PGP-based chart provenance system (`.prov` files) with native support for Sigstore/cosign signing and verification. The existing provenance mechanism, introduced in Helm 2, requires chart publishers to manage PGP keys and consumers to obtain and trust those keys manually. This friction has led to near-zero adoption in practice, leaving the vast majority of Helm charts deployed without any signature verification.

Sigstore's cosign has become the de facto signing standard in the container ecosystem, offering keyless signing via OIDC identity, transparency log integration through Rekor, and a dramatically simpler user experience. This proposal adds `helm sign` and `helm verify` subcommands backed by cosign, stores signatures as OCI artifacts alongside charts in OCI registries, and introduces a `cosign` verification mode for `helm install` and `helm upgrade`. The existing PGP-based `.prov` system remains available but is deprecated in favor of the new approach.

## Motivation

### The PGP Provenance Problem

Helm has supported chart provenance since Helm 2 through `.prov` files containing PGP signatures. Despite existing for years, this system sees almost no real-world usage. The reasons are well-documented:

**Key management burden:** Chart publishers must generate, secure, rotate, and distribute PGP keys. Consumers must discover, import, and decide to trust those keys. There is no standard keyserver or trust model for the Helm ecosystem, so every publisher invents their own distribution mechanism (README instructions, website downloads, out-of-band communication).

**Tooling friction:** The `helm package --sign` workflow requires a local PGP keyring. CI/CD pipelines must be configured with PGP secret keys, which creates secret management overhead. The `helm verify` command requires the public key to be pre-imported, which means consumers must perform manual setup before verification can occur.

**Ecosystem disconnect:** The container ecosystem has broadly adopted Sigstore/cosign for image signing. Organizations that sign their container images with cosign must use an entirely separate signing infrastructure for their Helm charts. This duplication is wasteful and confusing.

**No transparency or auditability:** PGP signatures provide no public transparency log. There is no way to audit when a chart was signed, by whom, or whether a key has been compromised without the publisher explicitly communicating revocation.

### Who Is Affected

- **Chart publishers** (e.g., Bitnami, major open-source projects, enterprise platform teams) who want to provide verifiable charts but find PGP too burdensome to set up and maintain.
- **Cluster operators and security teams** who want to enforce chart verification policies but cannot because the charts they consume are unsigned.
- **Enterprise compliance teams** who need audit trails for software supply chain integrity and cannot get them from the current system.
- **CI/CD pipeline authors** who must integrate signing into automated workflows and find PGP key management in pipelines painful.

### The Sigstore Opportunity

Sigstore has achieved broad adoption in the cloud-native ecosystem. Cosign is used to sign container images across major registries, and tools like Kyverno and OPA Gatekeeper can enforce cosign signature policies. By aligning Helm chart signing with the same infrastructure, chart verification becomes a natural extension of existing supply chain security practices rather than a separate, parallel system.

## Rationale

### Why Sigstore/Cosign Over Other Approaches

**Keyless signing via OIDC:** Cosign's keyless mode lets publishers sign charts using their existing identity (GitHub Actions OIDC, Google Cloud identity, etc.) without managing long-lived signing keys. This eliminates the single biggest barrier to adoption. A chart published from a GitHub Actions workflow can be signed automatically with zero key management.

**Transparency log (Rekor):** Every signature is recorded in an immutable, publicly auditable transparency log. This provides the auditability that PGP signatures lack and enables detection of compromised signing identities.

**OCI-native storage:** Cosign stores signatures as OCI artifacts alongside the signed content. Since Helm 3.8+ supports OCI registries as a first-class chart storage mechanism, cosign signatures fit naturally into the same registry infrastructure. No separate `.prov` file hosting is needed.

**Ecosystem alignment:** kubectl, Kyverno, OPA Gatekeeper, Tekton, and other CNCF projects already integrate with Sigstore. Using the same signing infrastructure for Helm charts means organizations can enforce unified supply chain policies across container images and Helm charts.

### How Other Projects Handle This

- **Container images:** Cosign is the standard. Registries like Docker Hub, GitHub Container Registry, and Amazon ECR support cosign signatures as OCI artifacts.
- **Kubernetes manifests:** The Kubernetes project signs release artifacts with cosign.
- **Linux packages:** Sigstore is being adopted for npm (via npmjs provenance), Python (via PEP 740), and other package ecosystems.

Helm is an outlier in the CNCF ecosystem by still relying exclusively on PGP for provenance.

### Key Tradeoffs

- **Dependency on Sigstore infrastructure:** Keyless signing requires access to Sigstore's Fulcio CA and Rekor transparency log (or self-hosted equivalents). This is acceptable because Sigstore infrastructure is operated by the Linux Foundation and has strong availability commitments, and organizations can run private instances.
- **Two signing systems during transition:** Maintaining both PGP and cosign signing adds complexity, but a clean break would strand the small number of existing PGP provenance users. Deprecation with a clear timeline is the pragmatic path.
- **OCI registry requirement for signatures:** Cosign signatures stored as OCI artifacts require an OCI-compatible registry. Charts distributed via HTTP repositories cannot use this signature storage mechanism, though they can use cosign with key-based signing and detached signatures.

## Specification

### New CLI Commands

#### `helm sign`

Signs a packaged chart (`.tgz`) using cosign.

```bash
# Keyless signing (uses OIDC identity, records in Rekor)
helm sign mychart-1.0.0.tgz

# Key-based signing
helm sign mychart-1.0.0.tgz --key cosign.key

# Sign and push signature to OCI registry
helm sign mychart-1.0.0.tgz --push oci://registry.example.com/charts

# Sign with custom Rekor and Fulcio endpoints (private Sigstore)
helm sign mychart-1.0.0.tgz \
  --rekor-url https://rekor.internal.example.com \
  --fulcio-url https://fulcio.internal.example.com
```

**Flags:**

| Flag | Default | Description |
|------|---------|-------------|
| `--key` | (none) | Path to cosign private key. If omitted, keyless signing is used. |
| `--push` | (none) | OCI registry reference to push signature to. |
| `--rekor-url` | `https://rekor.sigstore.dev` | Rekor transparency log URL. |
| `--fulcio-url` | `https://fulcio.sigstore.dev` | Fulcio CA URL for keyless signing. |
| `--output` | (none) | Write detached signature to file instead of pushing to registry. |
| `--tlog-upload` | `true` | Upload signature to transparency log. Set to `false` for air-gapped environments using key-based signing. |

#### `helm verify`

Verifies a chart's cosign signature.

```bash
# Verify using keyless identity (checks Rekor + Fulcio certificate)
helm verify mychart-1.0.0.tgz \
  --certificate-identity user@example.com \
  --certificate-oidc-issuer https://accounts.google.com

# Verify using a public key
helm verify mychart-1.0.0.tgz --key cosign.pub

# Verify a chart in an OCI registry (fetches signature from registry)
helm verify oci://registry.example.com/charts/mychart --version 1.0.0 \
  --certificate-identity-regexp '.*@example\.com' \
  --certificate-oidc-issuer https://accounts.google.com

# Verify with a detached signature file
helm verify mychart-1.0.0.tgz --signature mychart-1.0.0.tgz.sig --key cosign.pub
```

**Flags:**

| Flag | Default | Description |
|------|---------|-------------|
| `--key` | (none) | Path to cosign public key for key-based verification. |
| `--certificate-identity` | (none) | Expected signer identity for keyless verification (exact match). |
| `--certificate-identity-regexp` | (none) | Regex pattern for signer identity. |
| `--certificate-oidc-issuer` | (none) | Expected OIDC issuer for keyless verification. |
| `--certificate-oidc-issuer-regexp` | (none) | Regex pattern for OIDC issuer. |
| `--signature` | (none) | Path to detached signature file. |
| `--rekor-url` | `https://rekor.sigstore.dev` | Rekor URL for transparency log verification. |

### Verification on Install/Upgrade

The `helm install` and `helm upgrade` commands gain a `--verify-cosign` flag:

```bash
# Verify cosign signature before installing
helm install myrelease oci://registry.example.com/charts/mychart \
  --version 1.0.0 \
  --verify-cosign \
  --certificate-identity-regexp '.*@bitnami\.com' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

# Verify with public key
helm install myrelease oci://registry.example.com/charts/mychart \
  --version 1.0.0 \
  --verify-cosign \
  --key cosign.pub
```

When `--verify-cosign` is specified, the chart is not installed unless signature verification succeeds. This is distinct from the existing `--verify` flag, which uses PGP provenance.

### Signature Storage

For charts in OCI registries, cosign signatures are stored as OCI artifacts using cosign's standard tagging convention (`sha256-<digest>.sig`). This is the same mechanism used for container image signatures and requires no custom infrastructure.

For charts distributed outside of OCI registries (e.g., HTTP chart repositories), signatures can be stored as detached `.cosign.sig` files alongside the chart `.tgz` in the repository index, or verified against the Rekor transparency log by digest.

### Data Structures

The chart repository `index.yaml` gains an optional `cosignSignature` field:

```yaml
entries:
  mychart:
    - version: 1.0.0
      digest: sha256:abc123...
      urls:
        - https://example.com/charts/mychart-1.0.0.tgz
      cosignSignature:
        type: "detached"
        url: "https://example.com/charts/mychart-1.0.0.tgz.cosign.sig"
```

For OCI registries, no index changes are needed since cosign's standard OCI artifact discovery mechanism is used.

### Integration with `helm package`

A convenience flag is added to `helm package`:

```bash
# Package and sign in one step
helm package mychart/ --cosign-sign
helm package mychart/ --cosign-sign --cosign-key cosign.key
```

### Deprecation of PGP Provenance

The existing PGP-based `--sign`, `--verify`, and `--keyring` flags on `helm package`, `helm verify`, and `helm install` are deprecated but not removed. They will emit deprecation warnings directing users to the cosign-based equivalents. A future major version of Helm may remove PGP provenance support entirely.

### Edge Cases

- **Air-gapped environments:** Key-based signing with `--tlog-upload=false` supports environments without internet access to Sigstore infrastructure. Verification uses the public key directly without Rekor.
- **Multiple signatures:** A chart can have multiple cosign signatures (e.g., signed by both the chart author and an enterprise security review). `helm verify` succeeds if any provided identity/key matches.
- **Chart dependencies:** `helm dependency update` does not verify dependency signatures. Signature verification applies to the final packaged chart. A future HIP could address recursive dependency verification.
- **Helm plugins:** The signing and verification logic is implemented in Helm core, not as a plugin, to ensure consistent behavior and avoid the bootstrapping problem of needing to verify a plugin before using it.

## Backwards Compatibility

This proposal is fully backwards compatible. All changes are additive:

- **New commands:** `helm sign` and `helm verify` (with cosign) are new. The existing `helm verify` command for PGP provenance is preserved under `helm verify --legacy-pgp` (or simply continues to work when a `--keyring` is specified, since the flag combination is unambiguous).
- **New flags:** `--verify-cosign` on `helm install` / `helm upgrade` is new and opt-in. The existing `--verify` flag for PGP is unchanged.
- **Index format:** The `cosignSignature` field in `index.yaml` is optional. Older Helm clients ignore unknown fields.
- **OCI registries:** Cosign signatures as OCI artifacts do not interfere with chart storage or retrieval. Older Helm clients that do not understand cosign simply skip verification.

No existing workflow breaks. Users who currently use PGP provenance (a very small number) can continue to do so. The deprecation warning is informational and does not change behavior.

This feature is additive and appropriate for a minor version release.

## Security Implications

### Improvements Over Current System

- **Transparency log:** Rekor provides a public, append-only record of every signing event. If a signing key or identity is compromised, the transparency log enables detection and forensic analysis.
- **Short-lived certificates:** Keyless signing uses short-lived certificates (typically 10-minute validity) rather than long-lived PGP keys, reducing the window of exposure if credentials are compromised.
- **Identity-based trust:** Instead of trusting opaque PGP key IDs, consumers trust identifiable entities (email addresses, CI/CD pipeline identities) bound to OIDC issuers, making trust decisions more intuitive.

### Attack Surface Considerations

- **Sigstore infrastructure dependency:** Keyless signing depends on Fulcio and Rekor availability. If these services are unavailable, keyless signing fails. Mitigation: support key-based signing as a fallback, and support private Sigstore deployments.
- **OIDC identity compromise:** If an attacker compromises the OIDC identity used for signing (e.g., a GitHub Actions workflow token), they could sign malicious charts. Mitigation: the Rekor transparency log records all signing events, enabling detection. Organizations should monitor Rekor for unexpected signing events on their identities.
- **Signature stripping:** An attacker with registry write access could remove cosign signatures. Mitigation: `--verify-cosign` on install causes a hard failure if no valid signature is found, preventing installation of unsigned charts. Registry access controls remain the primary defense.
- **Cosign library vulnerabilities:** Embedding cosign's verification logic in Helm adds cosign's dependency tree to Helm's attack surface. Mitigation: use cosign as a well-maintained Go library with active security response, and track upstream releases.

### Misuse Scenarios

- A malicious chart author could sign a chart with a legitimate-looking but unrelated identity. Users must verify the `--certificate-identity` matches the expected publisher, not just that "a signature exists."
- Policy enforcement tools (Kyverno, OPA) should be used in production to codify trusted identities rather than relying on manual `--verify-cosign` invocations.

## How to Teach This

### Documentation Additions

1. **Chart Signing Guide:** A new top-level documentation page covering both keyless and key-based signing workflows, replacing the current provenance documentation as the recommended approach.
2. **Supply Chain Security Guide:** A conceptual guide explaining how cosign chart signing fits into a broader supply chain security strategy alongside image signing, SBOM generation, and policy enforcement.
3. **Migration Guide:** Step-by-step instructions for chart publishers currently using PGP provenance to switch to cosign signing.
4. **CI/CD Examples:** Ready-to-use workflow examples for GitHub Actions, GitLab CI, and other popular CI systems showing how to sign charts in automated pipelines.

### Key Example Pattern

The simplest and most common pattern for a chart publisher using GitHub Actions:

```yaml
# .github/workflows/release.yml
- name: Package and sign chart
  run: |
    helm package mychart/
    helm sign mychart-*.tgz --push oci://ghcr.io/${{ github.repository }}
```

For a consumer:

```bash
helm install myrelease oci://ghcr.io/org/charts/mychart \
  --version 1.0.0 \
  --verify-cosign \
  --certificate-identity-regexp '.*@myorg\.com' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

### How This Fits into Existing Helm Concepts

Signing and verification are presented as an optional but recommended step in the chart lifecycle: author, package, **sign**, push, **verify**, install. This mirrors the existing provenance concept but with dramatically lower friction. The `helm sign` / `helm verify` commands are direct analogs of the existing PGP provenance workflow, so users familiar with the old system can map concepts directly.

## Reference Implementation

No reference implementation exists yet. The implementation will involve:

1. Adding the `cosign` Go library (`github.com/sigstore/cosign/v2`) as a dependency to the Helm project.
2. Implementing `helm sign` and `helm verify` subcommands in `cmd/helm/`.
3. Adding `--verify-cosign` and related flags to `helm install` and `helm upgrade`.
4. Adding the `--cosign-sign` convenience flag to `helm package`.
5. Extending the OCI registry client to discover and store cosign signatures as OCI artifacts.
6. Adding the optional `cosignSignature` field to the repository index parser.
7. Adding deprecation warnings to the existing PGP provenance flags.
8. Comprehensive tests covering keyless signing, key-based signing, verification modes, air-gapped scenarios, and error handling.

A proof-of-concept branch will be linked here once development begins.

## Rejected Ideas

### Cosign as a Helm Plugin

Implementing signing as an external plugin (e.g., `helm-cosign`) was considered. This was rejected because:
- Plugins must themselves be trusted, creating a bootstrapping problem.
- Plugin installation is an extra step that reduces adoption.
- Core integration ensures consistent behavior across all Helm installations.
- The Helm project should own its supply chain security story.

### Notation (Microsoft) Instead of Cosign

Notation is another Sigstore-adjacent signing tool focused on the OCI ecosystem. It was rejected in favor of cosign because:
- Cosign has significantly broader adoption in the Kubernetes/CNCF ecosystem.
- Cosign's keyless signing mode is more mature.
- Most organizations already use cosign for container image signing.
- Supporting both would add complexity without proportional benefit. Notation support could be added in a future HIP if demand warrants it.

### Requiring Cosign for All Charts

Making chart signing mandatory was rejected because:
- It would break the existing ecosystem where nearly all charts are unsigned.
- Chart repositories and registries would need universal signing support.
- Development and testing workflows should not require signing infrastructure.
- Signing should be encouraged through tooling and documentation, not mandated.

### Removing PGP Provenance Immediately

A clean break from PGP was considered. This was rejected because:
- Some users may have invested in PGP provenance workflows.
- A deprecation period gives the community time to migrate.
- Both systems can coexist without technical conflict.

### Using In-Toto Attestations Instead of Raw Signatures

In-toto attestations provide richer metadata than raw signatures (e.g., build provenance, SBOM linkage). While valuable, this was rejected as the initial scope because:
- Raw signatures solve the immediate adoption problem with minimal complexity.
- In-toto attestation support can be layered on top in a future HIP.
- Cosign supports both raw signatures and attestations, so the foundation supports future extension.

## Open Issues

1. **Flag naming for legacy PGP:** Should the existing `--verify` flag be renamed to `--verify-pgp` or should it remain as-is with `--verify-cosign` being the new addition? The current proposal keeps `--verify` unchanged for backwards compatibility.
2. **Default verification in future major version:** Should a future Helm 4.x make `--verify-cosign` the default behavior for OCI registry installs? This is out of scope for this HIP but worth discussing.
3. **Recursive dependency verification:** Should `helm dependency update` verify cosign signatures on dependencies? This adds complexity and is deferred to a future proposal.
4. **Private Sigstore configuration:** How should private Fulcio/Rekor endpoints be configured persistently (environment variables, Helm configuration file, or both)?
5. **Cosign library versioning:** How will Helm track cosign library updates, and what is the compatibility commitment?
