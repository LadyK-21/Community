## Abstract

This HIP proposes replacing Helm's current PGP-based chart provenance system (`.prov` files) with native support for Sigstore/cosign signing and verification. The current provenance mechanism suffers from extremely low adoption due to the complexity of PGP key management, lack of integration with modern identity providers, and an opaque verification workflow. Sigstore provides keyless signing via OIDC identity, transparency logging via Rekor, and a verification model already established as the standard in the container image ecosystem. This proposal introduces `helm sign` and `helm verify` commands backed by cosign, stores signatures as OCI artifacts alongside chart packages in OCI registries, and maintains backward compatibility with the existing `.prov` system during a deprecation period.

## Motivation

### The Current State of Chart Provenance

Helm has supported chart provenance since Helm 2 through PGP-based `.prov` files. The system requires chart publishers to maintain PGP keypairs, distribute public keys out-of-band, and package `.prov` files alongside `.tgz` chart archives. Despite being available for years, adoption is negligibly low across the ecosystem. Several factors contribute to this:

**PGP key management is burdensome.** Publishers must generate keypairs, protect private keys, establish key rotation policies, and distribute public keys through a side channel. There is no standardized discovery mechanism for Helm chart signing keys. Users must manually locate, download, and import the correct public key before verification can occur.

**The verification workflow is disconnected.** Running `helm verify` requires the user to have already obtained and trusted the publisher's public key. There is no integration with any identity provider, certificate authority, or transparency log. Users have no easy way to determine whether a chart was signed by a legitimate publisher without prior out-of-band key exchange.

**The ecosystem has moved on.** The container ecosystem has converged on Sigstore (cosign, Rekor, Fulcio) as the standard for artifact signing and verification. Kubernetes itself, along with major container registries, CI/CD platforms, and policy engines, support Sigstore natively. Helm charts distributed as OCI artifacts sit in the same registries as container images but lack the same signing primitives.

**OCI registries are now first-class.** Helm 3.8+ supports OCI registries as a native chart storage backend. OCI registries support attaching signatures, attestations, and other metadata as associated artifacts (via the OCI Reference Types / Referrers API). The `.prov` file model predates OCI support and does not integrate with this ecosystem.

### Who Is Affected

- **Chart publishers** who want to sign their charts but are deterred by PGP complexity.
- **Chart consumers** who want to verify chart integrity and provenance before deploying to production clusters.
- **Platform and security teams** who need to enforce signing policies as part of supply chain security requirements.
- **CI/CD pipeline operators** who need automated, keyless signing integrated with workload identity.
- **Policy engine users** (OPA/Gatekeeper, Kyverno, Sigstore Policy Controller) who want to enforce chart signature verification using the same trust framework they use for container images.

### Real-World Impact

Supply chain security has become a critical concern across the cloud native ecosystem. Frameworks such as SLSA (Supply-chain Levels for Software Artifacts) require artifact signing as a baseline. Organizations that enforce container image signing via cosign today have no equivalent mechanism for Helm charts, creating a gap in their supply chain security posture. Native Sigstore support would close this gap and align Helm with the broader CNCF security ecosystem.

## Rationale

### Why Sigstore/Cosign

Sigstore is the CNCF's graduated project for software artifact signing. It provides three core components relevant to this proposal:

1. **Fulcio** - A free certificate authority that issues short-lived certificates tied to OIDC identities (GitHub Actions, Google, Microsoft, etc.). This enables "keyless" signing where the signer's identity is their existing OIDC identity rather than a long-lived PGP key.
2. **Rekor** - A transparency log that records signing events immutably. Anyone can verify that a signature was created at a specific time by a specific identity without needing to trust the signer's key distribution.
3. **Cosign** - The client tool (and Go library) for signing and verifying OCI artifacts. It already supports signing container images, SBOMs, attestations, and arbitrary blobs.

Cosign's Go library (`sigstore/cosign/v2`) is well-maintained, has a stable API, and is already used by numerous CNCF projects. Integrating it as a library dependency (rather than shelling out to the `cosign` CLI) provides a clean, testable integration.

### Why Not Notation (Notary v2)

Notation (the CNCF's other signing project, evolved from Notary v2) was considered. While Notation is a valid signing framework, cosign has significantly broader adoption in the Kubernetes ecosystem, is already the de facto standard for container image signing, and has a more mature Go library. Choosing cosign maximizes interoperability with existing toolchains. If Notation support is desired in the future, the proposed architecture allows additional signature backends to be added.

### Why OCI Artifact Signatures Instead of Files

The current `.prov` file approach stores signatures as separate files alongside chart `.tgz` archives. This model has several drawbacks: signature files can become separated from charts, classic chart repositories (index.yaml-based) have no formal association between a chart and its provenance file, and the model does not extend to OCI registries.

OCI registries support the Referrers API (OCI Distribution Spec 1.1), which allows artifacts (such as signatures) to be associated with a subject artifact (such as a chart). Cosign already uses this mechanism for container image signatures. Storing chart signatures as OCI reference artifacts keeps the signature co-located with the chart, discoverable via standard registry APIs, and consistent with how container image signatures work.

For charts distributed through classic (index.yaml) repositories rather than OCI registries, this proposal supports signing the chart `.tgz` as a blob and storing the signature bundle (Sigstore bundle format) as a `.cosign.bundle` file alongside the chart archive.

### Why Keyless by Default

Keyless signing (via Fulcio and OIDC) is the recommended default because it eliminates the key management problem that killed adoption of the PGP-based system. Publishers sign with their identity (e.g., a GitHub Actions workflow identity, a Google account, etc.) and the signature is recorded in the Rekor transparency log. Verifiers check the signature against the transparency log and a specified identity/issuer, without needing to obtain any keys in advance.

Key-based signing (using cosign-generated keypairs or KMS-backed keys) is also supported for environments that require it, such as air-gapped clusters or organizations with existing PKI infrastructure.

## Specification

### New Commands

#### `helm sign`

Signs a packaged chart (`.tgz`) or an OCI chart reference.

```bash
# Keyless signing (interactive OIDC flow)
helm sign mychart-1.0.0.tgz

# Keyless signing in CI (ambient OIDC credentials)
helm sign oci://registry.example.com/charts/mychart:1.0.0

# Key-based signing
helm sign mychart-1.0.0.tgz --key cosign.key

# KMS-backed signing
helm sign oci://registry.example.com/charts/mychart:1.0.0 --key awskms:///arn:aws:kms:us-east-1:123456789:key/abcd

# Sign and attach custom annotations
helm sign oci://registry.example.com/charts/mychart:1.0.0 \
  --annotations "org.example.build-url=https://ci.example.com/build/123"
```

**Behavior for OCI charts:** The signature is pushed to the same registry as a Referrer artifact associated with the chart manifest, using cosign's standard OCI media types.

**Behavior for `.tgz` files:** A Sigstore bundle file (`.cosign.bundle`) is written alongside the `.tgz`. The bundle contains the signature, certificate chain, and Rekor transparency log entry. This file replaces the role of the `.prov` file for new signing operations.

**Flags:**

| Flag | Description |
|------|-------------|
| `--key` | Path to a cosign private key, or a KMS URI. If omitted, keyless (OIDC) signing is used. |
| `--key-password` | Password for an encrypted cosign private key. If the key is encrypted and this flag is not provided, the user is prompted interactively. |
| `--identity-token` | An explicit OIDC identity token for keyless signing. If omitted, ambient credentials are detected (e.g., GitHub Actions OIDC, GCP metadata). |
| `--rekor-url` | URL of the Rekor transparency log (default: `https://rekor.sigstore.dev`). |
| `--fulcio-url` | URL of the Fulcio CA (default: `https://fulcio.sigstore.dev`). |
| `--tsa-url` | URL of a trusted timestamp authority. |
| `--annotations` | Key=value pairs to include in the signature payload (repeatable). |
| `--output-bundle` | Explicitly set the output path for the `.cosign.bundle` file (`.tgz` signing only). |
| `--allow-insecure-registry` | Allow signing charts in HTTP (non-TLS) registries. |

#### `helm verify`

Verifies the signature of a packaged chart or OCI chart reference.

```bash
# Keyless verification (requires specifying expected identity)
helm verify oci://registry.example.com/charts/mychart:1.0.0 \
  --certificate-identity "https://github.com/myorg/mychart/.github/workflows/release.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

# Keyless verification with identity regex
helm verify oci://registry.example.com/charts/mychart:1.0.0 \
  --certificate-identity-regexp ".*@myorg\\.com" \
  --certificate-oidc-issuer "https://accounts.google.com"

# Key-based verification
helm verify mychart-1.0.0.tgz --key cosign.pub

# Verify and display signature details
helm verify oci://registry.example.com/charts/mychart:1.0.0 \
  --certificate-identity "..." \
  --certificate-oidc-issuer "..." \
  --output json
```

**Behavior for OCI charts:** Signatures are discovered via the OCI Referrers API from the same registry. The chart digest is verified against the signature.

**Behavior for `.tgz` files:** The corresponding `.cosign.bundle` file is read from the same directory (or a path specified by `--bundle`). If a `.cosign.bundle` is not found, Helm falls back to checking for a `.prov` file and uses legacy PGP verification (with a deprecation warning).

**Flags:**

| Flag | Description |
|------|-------------|
| `--key` | Path to a cosign public key for key-based verification. |
| `--certificate-identity` | Expected identity in the signing certificate (required for keyless). |
| `--certificate-identity-regexp` | Regex pattern for the expected identity. |
| `--certificate-oidc-issuer` | Expected OIDC issuer (required for keyless). |
| `--certificate-oidc-issuer-regexp` | Regex pattern for the expected OIDC issuer. |
| `--rekor-url` | URL of the Rekor transparency log (default: `https://rekor.sigstore.dev`). |
| `--bundle` | Explicit path to a `.cosign.bundle` file (`.tgz` verification only). |
| `--output` | Output format: `text` (default) or `json`. |
| `--allow-insecure-registry` | Allow verifying charts in HTTP (non-TLS) registries. |

#### `helm install` / `helm upgrade` Integration

The `--verify` flag on `helm install` and `helm upgrade` is extended to support cosign verification.

```bash
# Verify before install using keyless verification
helm install myrelease oci://registry.example.com/charts/mychart:1.0.0 \
  --verify \
  --certificate-identity "https://github.com/myorg/mychart/.github/workflows/release.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

# Verify before install using key-based verification
helm install myrelease oci://registry.example.com/charts/mychart:1.0.0 \
  --verify \
  --key cosign.pub
```

When `--verify` is specified and the chart source is an OCI reference, Helm uses cosign verification. When the chart source is a `.tgz` file, Helm checks for a `.cosign.bundle` first and falls back to `.prov` if not found. When the chart source is a classic chart repository, existing PGP `.prov` verification behavior is preserved.

If `--verify` is specified and no valid signature is found through any mechanism, the command fails with a non-zero exit code.

### Signature Payload

For OCI charts, the signature payload is the chart manifest digest, consistent with how cosign signs container images.

For `.tgz` files, the signature payload is a JSON document containing:

```json
{
  "critical": {
    "type": "helm chart signature",
    "chart": {
      "name": "mychart",
      "version": "1.0.0"
    },
    "image": {
      "digest": "sha256:abc123..."
    }
  },
  "optional": {
    "annotations": {}
  }
}
```

The `digest` field contains the SHA-256 digest of the `.tgz` file, ensuring integrity verification.

### Configuration File

Users can set default verification policies in `~/.config/helm/sigstore.yaml` or via `$HELM_SIGSTORE_CONFIG`:

```yaml
# Default verification settings
defaults:
  rekor-url: https://rekor.sigstore.dev
  fulcio-url: https://fulcio.sigstore.dev

# Per-registry or per-repository trust policies
policies:
  - registry: "registry.example.com/charts/*"
    certificate-identity-regexp: ".*@example\\.com"
    certificate-oidc-issuer: "https://accounts.google.com"
  - registry: "ghcr.io/myorg/*"
    certificate-identity: "https://github.com/myorg/charts/.github/workflows/release.yml@refs/heads/main"
    certificate-oidc-issuer: "https://token.actions.githubusercontent.com"
```

When `--verify` is specified without explicit identity/issuer flags, Helm looks up the matching policy from this configuration. This allows organizations to configure trust policies once rather than specifying identity flags on every command invocation.

### Library / SDK Changes

The Helm SDK (`pkg/action`) is extended with:

```go
// SignOption configures chart signing
type SignOption struct {
    KeyRef          string   // Path to cosign key or KMS URI; empty for keyless
    IdentityToken   string   // Explicit OIDC token for keyless signing
    RekorURL        string   // Rekor transparency log URL
    FulcioURL       string   // Fulcio CA URL
    TSAUrl          string   // Timestamp authority URL
    Annotations     map[string]string
}

// VerifyOption configures chart verification
type VerifyOption struct {
    KeyRef                      string // Path to cosign public key
    CertificateIdentity         string // Expected signer identity
    CertificateIdentityRegexp   string // Regex for signer identity
    CertificateOIDCIssuer       string // Expected OIDC issuer
    CertificateOIDCIssuerRegexp string // Regex for OIDC issuer
    RekorURL                    string // Rekor transparency log URL
    BundlePath                  string // Explicit bundle path for .tgz files
}

// VerifyResult contains verification output
type VerifyResult struct {
    Verified    bool
    SignerIdentity string
    Issuer      string
    Timestamp   time.Time
    RekorLogID  string
    Annotations map[string]string
}
```

### Deprecation of PGP-Based Provenance

The existing PGP `.prov` system is deprecated but not removed in the initial release:

1. **Phase 1 (initial release):** `helm package --sign` and `helm verify` with PGP continue to work but emit a deprecation warning recommending migration to `helm sign` with cosign. The `--sign` flag on `helm package` is marked as deprecated in help text.
2. **Phase 2 (next major version, e.g., Helm 4):** PGP signing support is removed. `helm package --sign` is removed. `helm verify` only supports cosign. The `.prov` file format is no longer generated. Legacy `.prov` files are ignored with a warning.

During Phase 1, `helm verify` checks for cosign signatures first (OCI referrers or `.cosign.bundle`) and falls back to `.prov` if no cosign signature is found.

## Backwards Compatibility

### No Breaking Changes in Initial Release

- The existing `helm package --sign` and `helm verify` commands continue to function with PGP keys during the deprecation period.
- The existing `--verify` flag on `helm install`/`helm upgrade` continues to work with `.prov` files.
- Charts without signatures continue to install normally (signing is opt-in).
- The `--keyring` flag on existing commands continues to work.
- No changes to Chart.yaml, values.yaml, or any chart structure.

### Migration Path

Chart publishers can adopt cosign signing incrementally:

1. Start signing with cosign in addition to PGP (both signatures can coexist).
2. Update documentation to point consumers to cosign verification.
3. Drop PGP signing when the deprecation period ends.

Chart consumers can adopt cosign verification incrementally:

1. Configure trust policies in `sigstore.yaml`.
2. Start using `--verify` with cosign identity flags.
3. Remove PGP public keys from keyrings when no longer needed.

### Dependency Impact

This proposal adds `sigstore/cosign/v2` and its transitive dependencies to Helm's dependency tree. The cosign library is well-maintained and widely used, but it does increase the binary size and dependency surface. The cosign library dependencies are already part of the broader CNCF ecosystem and are actively maintained.

## Security Implications

### Improvements Over Current System

- **Elimination of long-lived keys.** Keyless signing uses short-lived certificates (typically 10-minute validity), reducing the window of exposure if credentials are compromised.
- **Transparency logging.** All signing events are recorded in Rekor, providing an auditable, tamper-evident log. If a signing key is compromised, the transparency log enables detection of unauthorized signatures.
- **Identity-based trust.** Verifiers specify *who* they trust (e.g., a GitHub Actions workflow in a specific repository) rather than managing opaque key material. This is more intuitive and harder to misconfigure.
- **Timestamp verification.** Signatures include trusted timestamps, enabling verification that a signature was created while the signing certificate was valid, even after the certificate expires.

### Potential Risks

- **Dependency on public infrastructure.** Keyless signing depends on Fulcio and Rekor being available. If these services experience downtime, keyless signing fails. Mitigation: key-based signing remains available as a fallback, and organizations can run private Sigstore infrastructure.
- **OIDC token exposure.** Keyless signing involves presenting an OIDC token to Fulcio. In CI environments, this token is typically scoped and short-lived. Users should ensure their OIDC tokens are appropriately scoped.
- **Trust in Sigstore root of trust.** Keyless verification trusts the Sigstore root CA (Fulcio) and transparency log (Rekor). Organizations with strict trust requirements can run private instances of these services using the `--rekor-url` and `--fulcio-url` flags.
- **Signature stripping.** An attacker with registry write access could delete signatures. Mitigation: Rekor provides an independent record that a signature existed. Registry access controls should be applied appropriately.
- **Malicious chart with valid signature.** A compromised publisher identity could sign a malicious chart. Mitigation: this is inherent to any signing system. The transparency log provides auditability, and consumers should scope their trust policies narrowly (e.g., specific workflow paths, not entire organizations).

### Air-Gapped Environments

For air-gapped environments without access to public Sigstore infrastructure:

- Key-based signing with cosign-generated keypairs works fully offline.
- Organizations can deploy private Sigstore stacks (Fulcio, Rekor, TUF root) within their network.
- The `--rekor-url`, `--fulcio-url`, and related flags support pointing to internal infrastructure.

## How to Teach This

### For Chart Publishers

**Getting started (keyless, CI):**

```bash
# In a GitHub Actions workflow:
- name: Sign Helm chart
  run: |
    helm package mychart/
    helm sign mychart-1.0.0.tgz
    helm push mychart-1.0.0.tgz oci://ghcr.io/myorg/charts
    # or, sign the chart already in the registry:
    helm sign oci://ghcr.io/myorg/charts/mychart:1.0.0
```

No key generation, no key storage, no key rotation. The GitHub Actions OIDC token is used automatically.

**Getting started (key-based):**

```bash
# One-time setup
cosign generate-key-pair

# Sign a chart
helm sign mychart-1.0.0.tgz --key cosign.key

# Distribute cosign.pub to consumers
```

### For Chart Consumers

**Verifying a chart (keyless):**

```bash
# Verify a chart from an OCI registry
helm verify oci://ghcr.io/myorg/charts/mychart:1.0.0 \
  --certificate-identity "https://github.com/myorg/charts/.github/workflows/release.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"

# Install with verification
helm install myrelease oci://ghcr.io/myorg/charts/mychart:1.0.0 \
  --verify \
  --certificate-identity "https://github.com/myorg/charts/.github/workflows/release.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com"
```

**Setting up trust policies:**

```bash
# Create a policy file so you don't need flags every time
cat > ~/.config/helm/sigstore.yaml <<EOF
policies:
  - registry: "ghcr.io/myorg/*"
    certificate-identity: "https://github.com/myorg/charts/.github/workflows/release.yml@refs/heads/main"
    certificate-oidc-issuer: "https://token.actions.githubusercontent.com"
EOF

# Now just use --verify
helm install myrelease oci://ghcr.io/myorg/charts/mychart:1.0.0 --verify
```

## Reference Implementation

No reference implementation exists yet. The implementation will:

1. Add `sigstore/cosign/v2` as a Go module dependency.
2. Implement the `helm sign` command in `cmd/helm/sign.go`.
3. Implement cosign verification in `cmd/helm/verify.go`, extending the existing verify command.
4. Extend `pkg/action` with `Sign` and `Verify` actions using the cosign Go library.
5. Extend `helm install` and `helm upgrade` to support cosign verification when `--verify` is specified.
6. Add the trust policy configuration file support.
7. Add deprecation warnings to the existing PGP signing codepath.
8. Include comprehensive unit and integration tests.
9. Update helm.sh documentation.

A proof-of-concept using the cosign Go library to sign and verify Helm chart `.tgz` files has been validated locally, confirming the feasibility of the library integration approach.

## Rejected Ideas

### Wrapping the cosign CLI instead of using the Go library

Shelling out to the `cosign` binary would introduce a runtime dependency, complicate installation, and make testing harder. The cosign Go library provides a stable API and avoids the need for users to install cosign separately.

### Making cosign the only signing method immediately

Removing PGP support without a deprecation period would break existing workflows for the small number of users who do use `.prov` files. A phased deprecation respects existing users while clearly signaling the direction.

### Adding Notation support alongside cosign

Supporting multiple signing backends in the initial implementation would increase complexity significantly. Cosign is the dominant standard in the Kubernetes ecosystem. Notation support can be considered as a future extension if demand materializes.

### Storing signatures in Chart.yaml or as chart files

Embedding signatures within the chart archive itself creates a chicken-and-egg problem (the archive digest changes when you add a file to it). Signatures must be external to the signed artifact.

### Using DSSE (Dead Simple Signing Envelope) directly instead of cosign

DSSE is a lower-level signing envelope format. Cosign provides DSSE support along with higher-level workflows (keyless signing, Rekor integration, OCI artifact handling) that would need to be reimplemented if using DSSE directly.

### Making verification mandatory

Requiring all charts to be signed would break the vast majority of existing workflows. Signing and verification should remain opt-in, with tooling that makes it easy enough that adoption grows organically.

### Creating a Helm-specific transparency log

Using a Helm-specific transparency log would fragment the ecosystem. Rekor is the established CNCF transparency log for software artifacts and benefits from shared infrastructure, monitoring, and trust.

## Open Issues

1. **Dependency tree size.** The cosign Go library brings a significant number of transitive dependencies. The impact on Helm's binary size and build times needs to be measured and evaluated. If the dependency footprint is too large, a lighter-weight integration using lower-level Sigstore libraries (`sigstore/sigstore-go`) could be explored.

2. **Classic chart repository support.** For charts served from classic (index.yaml) HTTP repositories rather than OCI registries, signature discovery is less standardized. The proposed `.cosign.bundle` sidecar file approach works but may need refinement. Should `index.yaml` be extended with a field for bundle URLs?

3. **Artifact Hub integration.** Artifact Hub currently shows provenance status based on `.prov` files. Coordination with Artifact Hub maintainers is needed to support displaying cosign signature status.

4. **Helm SDK consumers.** Tools that embed the Helm SDK (Flux, Argo CD, Terraform Helm provider, etc.) will need to be aware of the new verification options. Coordination with these projects will help ensure smooth adoption.

5. **Trust policy file location and format.** The proposed `~/.config/helm/sigstore.yaml` location and YAML format need community feedback. Should this integrate with the existing Helm environment variable and configuration conventions?

6. **Private Sigstore instances via TUF root.** For organizations running private Sigstore infrastructure, the verification flow needs a custom TUF root of trust. The exact mechanism for configuring this (file path, environment variable, flag) needs specification.

7. **Interaction with `helm dependency update`.** When chart dependencies are fetched, should their signatures be verified automatically if a trust policy exists? This could provide supply chain security for transitive dependencies but adds complexity.
