## Abstract

This proposal establishes a formal process for how the Helm project manages security embargoes and coordinates vulnerability disclosure with downstream distributors who package Helm. The current SECURITY.md documents how vulnerabilities are reported, triaged, and publicly disclosed, but it does not address the pre-disclosure coordination window during which downstream packagers (e.g., Linux distribution maintainers, cloud provider Helm integrations, and Homebrew/Chocolatey maintainers) need advance notice to prepare their own patched releases. This HIP defines an embargo timeline, a downstream notification list, eligibility criteria for joining that list, and obligations for participants, so that when a CVE is published, the broader Helm ecosystem can ship fixes in a coordinated manner rather than scrambling after the fact.

## Motivation

Today, when the Helm security team fixes a vulnerability, the patch and disclosure happen simultaneously. Downstream distributors who repackage Helm -- including Linux distributions (Fedora, Debian, Alpine, Arch), cloud providers (Azure, AWS, Google Cloud), and package managers (Homebrew, Chocolatey, Snap) -- learn about vulnerabilities at the same time as the general public. This creates several real-world problems:

1. **Delayed protection for users who install Helm through downstream channels.** A significant portion of Helm's user base installs Helm via their distribution's package manager rather than downloading the official binary. When a CVE is published, these users remain vulnerable for hours to days while downstream maintainers react, build, test, and publish updated packages.

2. **Inconsistent disclosure timing.** Without coordination, some downstream distributors may learn of the vulnerability through informal channels before the official disclosure, while others are caught off guard. This inconsistency creates confusion and an uneven security posture across the ecosystem.

3. **Pressure on downstream maintainers.** Distribution maintainers are forced into emergency response mode with no lead time, increasing the likelihood of rushed patches, missed testing, or delayed updates.

4. **Misalignment with industry norms.** Projects of comparable scale and adoption -- such as Kubernetes, Go, and OpenSSL -- operate formal embargo and coordinated disclosure processes. Helm's lack of one is an outlier and creates friction for distributors who already participate in similar programs for other CNCF projects.

The Helm project's SECURITY.md covers the reporting, triage, patch, and public disclosure phases well. What is missing is the step between "patch is ready" and "public disclosure" where trusted downstream distributors receive advance notice and the patch under embargo so they can prepare synchronized releases.

## Rationale

### Why a formal embargo list rather than ad-hoc notification

An ad-hoc approach -- where maintainers email known distributors on a case-by-case basis -- is error-prone and does not scale. A formal list with documented eligibility criteria, obligations, and removal procedures ensures consistent behavior across vulnerabilities and security team membership changes. It also provides transparency: distributors know exactly how to apply and what is expected of them.

### Why align with the Kubernetes model

Kubernetes operates a well-documented [private distributors list](https://kubernetes.io/docs/reference/issues-security/security-release-process/) that many Helm downstream distributors already participate in. Aligning Helm's process with the Kubernetes model reduces cognitive overhead for distributors who maintain both projects, and leverages a proven structure. However, Helm's process is intentionally smaller in scope given its smaller security team and lower vulnerability volume.

### Why a fixed embargo window rather than variable

A fixed default embargo period (7 calendar days with a maximum extension to 14 days) provides predictability for both the security team and downstream participants. Variable windows add coordination overhead and make it harder for distributors to plan their release schedules. The 7-day default balances giving distributors enough time to prepare against the risk of extended exposure if the vulnerability leaks.

### Why separate from the existing SECURITY.md

While this process extends the existing security workflow, codifying it as a HIP rather than simply amending SECURITY.md ensures the community formally reviews and approves the process. Once accepted, the relevant operational details will be incorporated into SECURITY.md, but the HIP serves as the authoritative design record.

## Specification

### Downstream Notification List

The Helm project will maintain a private mailing list (e.g., `cncf-helm-distros@lists.cncf.io`) for pre-disclosure notification of security vulnerabilities. This list is separate from the existing `cncf-helm-security@lists.cncf.io` list, which is used for inbound vulnerability reports.

### Eligibility Criteria

Organizations or individuals may apply to join the downstream notification list if they meet **all** of the following criteria:

1. **Active distribution**: The applicant actively packages and distributes Helm to end users through a publicly available channel (e.g., a Linux distribution repository, a cloud provider's managed service, or a public package manager).
2. **Demonstrated user base**: The distribution channel serves a non-trivial user base. Self-assessment is acceptable, but the security team may request evidence.
3. **Security response capability**: The applicant has the ability to produce and ship patched builds within the embargo window.
4. **Embargo compliance history**: The applicant has not previously violated an embargo from any open source project's coordinated disclosure process, or any previous violation has been remediated and documented.

### Application Process

1. An applicant sends a request to `cncf-helm-security@lists.cncf.io` with:
   - The name of the distribution or product
   - A description of how Helm is packaged and distributed
   - An estimate of the user base
   - Contact information for the applicant's security response team (minimum two contacts)
   - A statement agreeing to abide by the embargo obligations

2. The Helm security team reviews the application. Approval requires agreement from at least two security team members.

3. Approved applicants are added to the `cncf-helm-distros` mailing list.

4. The list of member organizations (not individual contacts) is published in SECURITY.md for transparency.

### Removal from the List

Members may be removed from the downstream notification list under the following circumstances:

- **Voluntary withdrawal**: A member may leave at any time by notifying the security team.
- **Embargo violation**: If a member discloses vulnerability details before the embargo lifts, they are immediately removed. Reinstatement requires a new application after a minimum 12-month waiting period.
- **Inactivity**: If a member's distribution is discontinued or the member fails to respond to two consecutive embargo notifications, the security team may remove them after a 30-day notice period.

### Embargo Process

When the Helm security team has confirmed a vulnerability and developed a fix, the following process applies:

1. **Day 0 (Patch Ready)**: The security team finalizes the patch and determines the embargo timeline.

2. **Day 0-1 (Notification)**: The security team sends a notification to the `cncf-helm-distros` mailing list containing:
   - A description of the vulnerability (including affected versions)
   - The severity assessment (CVSS score if available)
   - The patch or a link to a private repository branch containing the fix
   - The planned public disclosure date (the "embargo lift date")
   - Any available workarounds

3. **Days 1-7 (Embargo Period)**: Downstream distributors prepare their patched releases but do NOT publish them or disclose any details. During this period:
   - Distributors may ask clarifying questions on the `cncf-helm-distros` list
   - The security team is available for technical questions about the patch
   - Distributors MUST NOT share the vulnerability details, patch, or existence of the embargo with anyone outside their immediate security response team

4. **Day 7 (Public Disclosure)**: The Helm project publishes the patched release, blog post, and mailing list announcement per the existing SECURITY.md process. Downstream distributors may publish their patched packages simultaneously or as soon as they are ready after this point.

### Timeline Adjustments

- The default embargo period is **7 calendar days**.
- The security team may **shorten** the embargo (minimum 2 days) if the vulnerability is actively being exploited in the wild or if there is credible evidence of an imminent leak.
- The security team may **extend** the embargo (maximum 14 calendar days) if downstream distributors request additional time and the risk of leak remains low.
- Any timeline adjustment is communicated to all downstream notification list members.

### Severity Threshold

Not all vulnerabilities warrant a full embargo process. The embargo and coordinated disclosure process applies to vulnerabilities that meet **any** of the following:

- CVSS base score of 7.0 or higher (High or Critical severity)
- The vulnerability allows remote code execution, privilege escalation, or credential disclosure
- The security team determines the vulnerability has high potential for real-world exploitation

For lower-severity vulnerabilities, the security team may choose to follow the existing SECURITY.md process (fix and disclose simultaneously) at their discretion.

### Record Keeping

The security team will maintain a private log of each embargo event including:

- The vulnerability identifier (CVE ID once assigned)
- The embargo start and end dates
- Any timeline adjustments and the rationale
- A list of downstream members who were notified
- Any incidents (e.g., leaks, late notifications)

This log is accessible only to security team members and is used for process improvement.

## Backwards compatibility

This proposal is purely additive to the existing security process. It does not change how vulnerabilities are reported, triaged, or publicly disclosed. The existing SECURITY.md workflow remains intact; this HIP adds a new step between the "patch ready" and "public disclosure" phases.

Downstream distributors who do not join the notification list are unaffected -- they continue to learn about vulnerabilities through public disclosure as they do today.

## Security implications

### Increased attack surface from pre-disclosure sharing

Sharing vulnerability details with a wider group before public disclosure inherently increases the risk of a leak. This risk is mitigated by:

- Strict eligibility criteria for joining the notification list
- Clear obligations and consequences for embargo violations (immediate removal, 12-month waiting period)
- Limiting the notification to organizations with a demonstrated need (active distributors with a user base)
- Keeping the list membership small and publishing the list of member organizations for accountability

### Risk of a compromised member

If a downstream notification list member's infrastructure is compromised, an attacker could learn about vulnerabilities before the public disclosure. This is an inherent risk of any coordinated disclosure program and is accepted as a tradeoff for the benefit of synchronized patching. Mitigations include:

- Requiring members to have a security response capability (implying baseline security practices)
- Using encrypted email (PGP) for embargo notifications
- Keeping the embargo window short (7 days default, 14 days maximum) to minimize the exposure window

### Improved overall security posture

Despite the risks above, the net security impact is positive. Coordinated disclosure means a larger portion of the Helm user base receives patched versions on or near disclosure day, reducing the window during which users are exposed to known vulnerabilities.

## How to teach this

### For vulnerability reporters

No change to the existing reporting process. Reporters continue to email `cncf-helm-security@lists.cncf.io` as described in SECURITY.md. The reporter may be informed that their report will be subject to an embargo period before public disclosure, but no action is required from them.

### For downstream distributors

The SECURITY.md file will be updated with a new "Coordinated Disclosure for Downstream Distributors" section that explains:

- What the downstream notification list is and why it exists
- How to apply for membership
- What to expect during an embargo (notification content, timeline, obligations)
- Consequences of violating the embargo

An announcement will be sent to the `cncf-helm` mailing list when this process goes live, inviting known downstream distributors to apply.

### For Helm users

Users installing Helm through downstream channels benefit automatically -- they receive patched packages faster. No user-facing documentation changes are required. The Helm blog post accompanying each security release may note that coordinated disclosure was performed, providing transparency.

### For the Helm security team

An internal runbook will be created (maintained alongside the private embargo log) documenting the step-by-step process for initiating an embargo, sending notifications, managing the timeline, and handling violations. This runbook is not part of the HIP but is an expected implementation artifact.

## Reference implementation

The reference implementation consists of:

1. **Mailing list creation**: Request the CNCF to provision `cncf-helm-distros@lists.cncf.io` as a private, moderated mailing list managed by the Helm security team.

2. **SECURITY.md update**: Add a "Coordinated Disclosure for Downstream Distributors" section to the existing [SECURITY.md](https://github.com/helm/community/blob/main/SECURITY.md) covering the application process, eligibility criteria, and embargo obligations.

3. **Notification template**: Create a standard notification email template for the security team to use when initiating an embargo. This template will be stored in the security team's private documentation.

4. **Initial outreach**: Contact known downstream distributors (Fedora, Debian, Alpine, Homebrew, Chocolatey, Snap, and major cloud providers) to inform them of the new process and invite applications.

No code changes are required. The reference implementation is complete when the mailing list is operational and SECURITY.md has been updated.

## Rejected ideas

### Using a shared private GitHub repository instead of a mailing list

A private GitHub repository for sharing patches was considered but rejected because:

- It requires all downstream contacts to have GitHub accounts, which may not be the case for all distribution maintainers
- Access control on GitHub repositories is less granular than a mailing list (repository access implies access to all past embargoes)
- The Kubernetes project uses a mailing list for the same purpose, and alignment reduces friction for shared downstream maintainers

### Per-vulnerability opt-in notifications

An approach where downstream distributors would be notified about the existence of an embargo and then opt in to receive details was considered. This was rejected as it adds unnecessary round-trip latency during a time-sensitive process. Distributors on the list have already agreed to the obligations; adding an opt-in step for each vulnerability slows down the process without meaningful security benefit.

### Unlimited embargo extensions

Allowing indefinite embargo extensions at the request of downstream distributors was rejected. Open-ended embargoes increase the risk of leaks and delay protection for users who install Helm directly. The 14-day maximum ensures the process moves forward even if some distributors are not ready.

### Including chart repositories in the downstream notification list

The scope was considered for extending to Helm chart repository operators (e.g., Artifact Hub, Bitnami). This was rejected because chart repository operators do not repackage the Helm binary and are not in the critical path for patching Helm CLI or library vulnerabilities. If a vulnerability affects a chart specification or convention, a separate process may be warranted in the future.

## Open issues

1. **PGP vs. age encryption**: The current SECURITY.md references PGP keys for the security team. Should embargo notifications also use PGP encryption, or should a more modern tool like [age](https://age-encryption.org/) be supported? This depends on what downstream distributors can support.

2. **CNCF mailing list logistics**: The CNCF manages the `lists.cncf.io` infrastructure. It needs to be confirmed that they can provision a private, moderated list with the access controls needed (only security team members can post, membership managed by the security team).

3. **Interaction with Kubernetes embargo**: Many Helm vulnerabilities may relate to Kubernetes interactions. When a vulnerability affects both projects, the embargo timelines should be coordinated. The exact mechanism for cross-project embargo coordination is left as an open issue to be resolved with the Kubernetes security team.

4. **Maximum list size**: Should there be a cap on the number of downstream notification list members? A larger list increases leak risk but also increases the proportion of users protected at disclosure time. The initial approach is to rely on eligibility criteria rather than a hard cap, but this should be revisited after the first year of operation.
