## Abstract

This proposal establishes a formal process for how the Helm project manages security embargoes and coordinates vulnerability disclosure with downstream distributors who package Helm. The current [SECURITY.md][SECURITY.md] documents how vulnerabilities are reported and publicly disclosed, but it does not address the period between initial triage and public release -- specifically, how and when downstream distributors (Linux distributions, managed Kubernetes providers, container image builders, and other repackagers) are notified so they can prepare patches in advance of a public CVE announcement. This HIP defines the embargo lifecycle, the criteria for downstream distributor membership, communication protocols, and the obligations of all parties involved.

## Motivation

Helm is one of the most widely deployed tools in the Kubernetes ecosystem. It is packaged and redistributed by a large number of downstream consumers, including but not limited to:

- Linux distributions (e.g., Debian, Fedora, Alpine, Homebrew, Chocolatey)
- Managed Kubernetes providers and cloud platforms
- Container image builders (e.g., official Helm container images)
- Enterprise Kubernetes distributions
- Internal corporate repositories that vendor Helm binaries

When a security vulnerability is discovered in Helm, the current process (documented in [SECURITY.md][SECURITY.md]) covers reporting, triage, patching, and public disclosure. However, it is silent on how downstream distributors learn about vulnerabilities before the public announcement. This creates several problems:

1. **Delayed protection for users.** If distributors learn about a vulnerability only at the moment of public disclosure, their users remain exposed during the time it takes to rebuild, test, and publish updated packages. For some distributions with multi-stage release processes, this window can last days or weeks.

2. **Inconsistent ad-hoc communication.** Without a formal process, individual maintainers may privately notify some distributors they happen to know while others receive no advance notice. This creates inequitable access to security information and inconsistent user protection.

3. **Risk of premature disclosure.** Without clear embargo rules, well-intentioned but informal sharing of vulnerability details increases the risk that information leaks before a coordinated fix is available, potentially exposing all users.

4. **Lack of accountability.** Without documented expectations for both the Helm security team and downstream distributors, there is no framework for addressing embargo violations or establishing trust relationships.

5. **Alignment with CNCF ecosystem practices.** Other major CNCF projects (Kubernetes, Envoy, containerd) maintain formal distributor notification lists and embargo processes. Helm's absence of such a process is a gap relative to peer projects.

This HIP is necessary because the gap cannot be addressed through informal convention alone. A documented process provides clarity, consistency, and accountability for all parties.

## Rationale

The design of this process is informed by several key considerations:

### Why a tiered notification model

Not all downstream consumers have the same needs or the same capacity to handle embargoed information securely. A tiered approach allows the Helm project to notify a small, trusted set of distributors early (giving them maximum lead time) while still providing advance notice to a broader group closer to the public disclosure date. This balances the need for early preparation against the risk that broader distribution increases the chance of leaks.

### Why formalize distributor membership criteria

An open-ended "notify whoever asks" approach does not scale and does not provide accountability. By establishing clear criteria for joining the distributor notification list -- including demonstrated user base, ability to act on embargoed information, and willingness to abide by embargo terms -- the Helm project can maintain a manageable, trustworthy set of partners.

### Why model after Kubernetes and other CNCF projects

The Kubernetes project's [private distributors list][k8s-distros] has been operating successfully for years and has established norms that many downstream distributors are already familiar with. Aligning Helm's process with these norms reduces friction for distributors who already participate in other CNCF embargo processes and leverages proven practices.

### Why define explicit timelines

Ambiguity about when notifications happen and when embargoes lift leads to confusion and potentially premature disclosure. Explicit timelines (even if approximate) give all parties a shared framework for planning.

### Why include an embargo violation policy

Trust is the foundation of any embargo process. Without consequences for violations, the process has no teeth. However, the policy must also be fair, recognizing that accidental disclosures differ from negligent or intentional ones.

## Specification

### Definitions

- **Embargo**: A period during which information about a security vulnerability is restricted to authorized parties and must not be publicly disclosed.
- **Embargo Start**: The point at which the Helm security team confirms a reported vulnerability and begins developing a fix.
- **Embargo End**: The point at which the vulnerability is publicly disclosed, typically coinciding with the release of a patched version of Helm.
- **Downstream Distributor**: An organization or individual that repackages, redistributes, or otherwise makes Helm available to end users through channels other than the official Helm release artifacts.
- **Security Team**: The subset of Helm maintainers responsible for handling vulnerability reports, as defined in [SECURITY.md][SECURITY.md].
- **Distributor Notification List**: A private, access-controlled mailing list or communication channel used to share embargoed vulnerability information with approved downstream distributors.

### Embargo Lifecycle

The embargo process consists of the following phases:

#### Phase 1: Report and Triage (Day 0 to Day 3)

This phase is already documented in [SECURITY.md][SECURITY.md] and remains unchanged. A vulnerability is reported to `cncf-helm-security@lists.cncf.io`, and the security team acknowledges receipt within 3 business days.

During this phase:
- The security team assesses the validity and severity of the report
- A preliminary severity rating is assigned (Critical, High, Medium, Low) using CVSS v3.1 or later as guidance
- The security team determines whether the issue warrants an embargo (not all issues do; see "Embargo Criteria" below)

#### Phase 2: Fix Development (Day 3 to Embargo End minus 7 days)

During this phase:
- The security team and relevant maintainers develop a fix in a private repository or branch
- The fix undergoes internal review and testing
- A target public disclosure date is set by the security team
- The disclosure date SHOULD allow at least 14 calendar days from the initial report for Critical and High severity issues, and at least 7 calendar days for Medium and Low severity issues, though these timelines may be adjusted based on complexity and risk

#### Phase 3: Distributor Pre-notification (Embargo End minus 7 days to Embargo End minus 1 day)

This is the new phase introduced by this HIP.

- **7 calendar days** before the planned public disclosure, the security team sends a notification to the Distributor Notification List containing:
  - A description of the vulnerability
  - Affected versions
  - Severity rating
  - The planned disclosure date and time (in UTC)
  - Patch details or a link to the embargoed fix (when available)
  - Any known workarounds
  - The embargo end date and time
  - Instructions on how to obtain pre-release patched binaries or source (if applicable)

- For **Critical severity** vulnerabilities that are known to be actively exploited in the wild, the security team MAY shorten the pre-notification period to as little as 24 hours if a faster response is deemed necessary to protect users.

- For vulnerabilities that require extended fix development (more than 30 days), the security team MAY send an early advisory to the Distributor Notification List with limited details (affected component, severity estimate, expected timeline) up to 14 days before the full pre-notification. This early advisory MUST NOT include specific technical details of the vulnerability.

#### Phase 4: Public Disclosure (Embargo End)

This phase is already documented in [SECURITY.md][SECURITY.md] and remains largely unchanged:
- A patched release is published
- A disclosure blog post is published on the [Helm Blog][helm-blog]
- The disclosure is emailed to the [Helm mailing list][helm-mailing-list]
- CVE assignment is initiated (or the pre-assigned CVE is made public)

Additionally, this HIP adds:
- A notification is sent to the Distributor Notification List confirming that the embargo has been lifted
- Distributors are free to publish their own advisories and updated packages

#### Phase 5: Post-Disclosure (Embargo End plus 1 to 30 days)

- The security team conducts a brief retrospective for Critical and High severity vulnerabilities to evaluate the effectiveness of the embargo process
- Any issues with the embargo process (such as premature leaks or communication failures) are documented and addressed
- The CVE ID is obtained and linked to the disclosure (if not already assigned)

### Embargo Criteria

Not all vulnerabilities require a full embargo process. The security team SHALL apply the embargo process when:

- The vulnerability is rated **Critical** or **High** severity
- The vulnerability is in Helm's core functionality (the `helm/helm` repository)
- A fix is not yet available and public knowledge of the vulnerability could enable exploitation

The security team MAY apply the embargo process when:

- The vulnerability is rated **Medium** severity
- The vulnerability is in a Helm sub-project that has significant user impact

The security team SHOULD NOT apply the embargo process when:

- The vulnerability is rated **Low** severity
- A fix is already publicly available (e.g., in a dependency update)
- The vulnerability is already publicly known

### Distributor Notification List

#### Communication Channel

The Distributor Notification List SHALL be implemented as a private mailing list hosted by the CNCF, following the same infrastructure patterns used by other CNCF projects. The address SHALL be `cncf-helm-distributors-announce@lists.cncf.io`.

The list SHALL be configured as follows:
- Only the Helm security team members may post to the list
- Subscriber addresses are not visible to other subscribers
- Archives are disabled
- The list is not publicly discoverable

#### Membership Criteria

To join the Distributor Notification List, an organization or individual must meet ALL of the following criteria:

1. **Active distribution**: The applicant must actively package, redistribute, or otherwise make Helm available to end users through a publicly accessible distribution channel. Examples include Linux distribution package repositories, cloud provider tool repositories, and container image registries.

2. **Significant user base**: The distribution channel must serve a non-trivial number of Helm users. The security team will evaluate this qualitatively; there is no strict numerical threshold. Indicators include: public download statistics, inclusion in a major Linux distribution, or status as a managed Kubernetes provider.

3. **Ability to act**: The applicant must demonstrate the ability to produce and publish updated packages within a reasonable timeframe (generally within 72 hours of embargo end for Critical vulnerabilities, and within 7 days for other severities).

4. **Security capability**: The applicant must have personnel and processes capable of securely handling embargoed information. At minimum, the applicant must designate a primary and secondary contact who can receive and act on notifications.

5. **Agreement to embargo terms**: The applicant must explicitly agree to the embargo obligations described in this HIP.

#### Application Process

1. The applicant sends a request to `cncf-helm-security@lists.cncf.io` with the subject line "Distributor Notification List Application" containing:
   - Organization name
   - Distribution channel(s) and approximate user base
   - Primary and secondary contact names and email addresses
   - A brief description of their security handling processes
   - Acknowledgment of the embargo obligations in this HIP

2. The security team reviews the application and votes. A simple majority of security team members is required for approval.

3. Approved applicants are added to the Distributor Notification List and notified of their acceptance.

4. Denied applicants are notified with a brief explanation. They may reapply after 6 months or when circumstances change.

#### Membership Maintenance

- Members MUST update their contact information within 14 days of any personnel changes by emailing `cncf-helm-security@lists.cncf.io`.
- The security team SHALL conduct an annual review of the Distributor Notification List membership. Members who no longer meet the criteria, or who have been unresponsive to test notifications, will be removed.
- Members MAY voluntarily leave the list at any time by emailing `cncf-helm-security@lists.cncf.io`.
- Members who violate embargo terms are subject to the violation policy described below.

### Embargo Obligations

All parties with access to embargoed vulnerability information are bound by the following obligations:

#### Obligations of the Helm Security Team

1. Provide accurate and timely notifications to the Distributor Notification List as described in the embargo lifecycle.
2. Clearly communicate the embargo end date and time in all notifications.
3. Provide sufficient technical detail for distributors to prepare patches.
4. Make a good-faith effort to adhere to the communicated timeline. If the timeline must change, notify the Distributor Notification List promptly with the updated schedule.
5. Maintain the confidentiality of Distributor Notification List membership.

#### Obligations of Distributor Notification List Members

1. **Confidentiality**: Embargoed information MUST NOT be shared with anyone outside the member's organization who does not have a direct need to know in order to prepare the fix. Specifically:
   - Information MUST NOT be shared in public forums, issue trackers, or chat channels
   - Information MUST NOT be shared with individuals who are not directly involved in preparing the updated package
   - Binary or source patches MUST NOT be published to public repositories before the embargo ends
2. **Timely action**: Members SHOULD prepare updated packages during the embargo period so they can be published promptly when the embargo lifts.
3. **No early publication**: Updated packages and advisories MUST NOT be made available to end users before the embargo end date, even in "testing" or "unstable" channels that are publicly accessible.
4. **Communication**: Members MUST acknowledge receipt of embargo notifications within 24 hours (business hours) by replying to `cncf-helm-security@lists.cncf.io`.
5. **Incident reporting**: If a member becomes aware that embargoed information has been or may have been leaked, they MUST immediately notify `cncf-helm-security@lists.cncf.io`.

### Embargo Violation Policy

Violations of embargo obligations are handled as follows:

1. **First unintentional violation** (e.g., accidental publication to a public staging repository that is quickly reverted): The security team issues a written warning and works with the member to prevent recurrence. No change in membership status.

2. **Repeated unintentional violations or a single negligent violation**: The member's access to the Distributor Notification List is suspended for 6 months. The member may reapply after the suspension period.

3. **Intentional violation** (e.g., deliberately publishing vulnerability details before the embargo lifts without security team authorization): The member is permanently removed from the Distributor Notification List. The security team will also notify the CNCF TOC of the violation.

4. **Emergency acceleration**: If an embargo is violated by any party (member or otherwise), the security team MAY accelerate the public disclosure timeline to protect users. In such cases, the security team SHALL notify all Distributor Notification List members of the accelerated timeline.

The security team determines the classification of violations. Members may appeal to the Helm org maintainers if they disagree with the security team's classification.

### Integration with Existing SECURITY.md

Upon acceptance of this HIP, the [SECURITY.md][SECURITY.md] document SHALL be updated to:

1. Add a new "Coordinated Disclosure with Downstream Distributors" section referencing this HIP
2. Add a brief description of the Distributor Notification List and how to apply
3. Link to this HIP for the full process details

The existing content of [SECURITY.md][SECURITY.md] regarding reporting, triage, the security team, and public disclosure remains unchanged except where this HIP explicitly modifies it.

## Backwards compatibility

This HIP introduces a new process that does not alter any existing documented process. The current vulnerability reporting, triage, and public disclosure workflows described in [SECURITY.md][SECURITY.md] remain intact. This HIP adds a new phase (distributor pre-notification) between fix development and public disclosure.

Organizations and individuals who do not join the Distributor Notification List will continue to learn about vulnerabilities through the existing public disclosure process and are not affected by this HIP.

## Security implications

This HIP improves the Helm project's overall security posture by:

1. **Reducing the window of exposure** for users of downstream distributions by enabling distributors to have updated packages ready at or near the time of public disclosure.
2. **Reducing the risk of ad-hoc leaks** by replacing informal, unstructured communication with a formal, accountable process.
3. **Establishing accountability** through clear membership criteria, obligations, and a violation policy.

However, this HIP also introduces new risks that must be managed:

1. **Expanded attack surface for information leaks**: Every additional party notified of a vulnerability before public disclosure increases the risk of a premature leak. This is mitigated by the membership criteria, embargo obligations, and violation policy.
2. **Operational burden on the security team**: Managing the Distributor Notification List, reviewing applications, and conducting annual reviews requires ongoing effort. This is mitigated by keeping the process lightweight and leveraging CNCF-hosted infrastructure.
3. **Trust dependencies**: The process depends on distributor members honoring their obligations. The violation policy provides deterrence, but cannot prevent a determined bad actor. This is an inherent limitation of any embargo process.

## How to teach this

1. **SECURITY.md update**: The primary touchpoint for this process is the [SECURITY.md][SECURITY.md] document, which will be updated to reference this HIP and provide instructions for distributors who wish to join the notification list.

2. **Blog post**: Upon acceptance, a blog post on the [Helm Blog][helm-blog] will announce the new process and invite eligible downstream distributors to apply for membership.

3. **KubeCon announcement**: The process will be announced at the next KubeCon/CloudNativeCon Helm maintainer session to ensure visibility within the CNCF community.

4. **Direct outreach**: The security team will identify and directly contact known major downstream distributors of Helm to inform them of the new process and invite applications.

5. **Dev meeting**: The contents of this HIP will be discussed in the public Helm Dev meeting, which is recorded.

## Reference implementation

The reference implementation consists of the following actions, to be completed upon acceptance of this HIP:

1. **Create the mailing list**: Request creation of `cncf-helm-distributors-announce@lists.cncf.io` from the CNCF, configured as described in this HIP.
2. **Update SECURITY.md**: Add the "Coordinated Disclosure with Downstream Distributors" section as described in the "Integration with Existing SECURITY.md" section of this HIP.
3. **Initial outreach**: Contact known downstream distributors to invite applications.
4. **Template creation**: Create a notification template for the security team to use when sending embargo notifications, ensuring consistency and completeness of information shared.

## Rejected ideas

### 1. Using a shared private GitHub repository instead of a mailing list

A private GitHub repository was considered as the communication channel for distributor notifications. This was rejected because:
- GitHub does not provide fine-grained controls over notification visibility in the way a mailing list does
- Repository access management is more complex than mailing list subscriber management
- Email notifications are more reliable for time-sensitive security communications than GitHub notifications, which can be missed or delayed
- The CNCF already hosts mailing list infrastructure that other projects use for this purpose

### 2. Fully open embargo process with public pre-announcements

An approach where the Helm project publicly pre-announces that a security fix is coming (without details) was considered. While this provides some advance warning, it was rejected as insufficient because:
- It does not give distributors enough information to prepare patches
- Public pre-announcements can attract unwanted attention from malicious actors who may attempt to reverse-engineer the vulnerability from the fix
- It does not address the core need for distributors to have actionable technical details before public disclosure

### 3. Delegating the entire process to the CNCF Security TAG

Delegating embargo management to the CNCF Security Technical Advisory Group was considered. This was rejected because:
- The CNCF Security TAG provides guidance and tooling but does not operate project-level security processes
- Helm's security team has the most context about Helm-specific vulnerabilities and is best positioned to manage the embargo
- Other CNCF projects (Kubernetes, Envoy) manage their own distributor lists rather than delegating to the Security TAG

### 4. No formal membership criteria (open to anyone who asks)

An open model where any party could join the notification list by simply requesting access was considered. This was rejected because:
- It would be impossible to maintain accountability with an unbounded set of recipients
- The risk of premature disclosure increases linearly with the number of parties who have access
- Without criteria, the security team would have no basis for removing members who do not act on notifications or who lack the capacity to handle embargoed information

### 5. Longer default pre-notification period (14 or 30 days)

Longer pre-notification windows were considered. These were rejected because:
- The longer the embargo period, the higher the risk of information leaks
- 7 days provides sufficient time for most distributors to prepare updated packages
- For complex issues, the early advisory mechanism provides additional lead time without full technical disclosure
- This aligns with the practices of comparable CNCF projects

## Open issues

1. **Initial list of distributors**: The security team should identify and reach out to known downstream distributors of Helm to seed the initial Distributor Notification List. A non-exhaustive list of candidates includes: Homebrew, Chocolatey, Alpine Linux, Debian, Fedora, Arch Linux, Snap, and major cloud providers that distribute Helm. The exact initial membership will be determined during implementation.

2. **CNCF infrastructure availability**: The creation of `cncf-helm-distributors-announce@lists.cncf.io` depends on CNCF infrastructure team support. If the CNCF is unable to host this list, an alternative hosting solution will need to be identified.

3. **Interaction with Helm 4 release process**: If this HIP is accepted during the Helm 4 development cycle (see [HIP-0012][hip-0012]), the process should be operational before Helm 4's release to ensure any security issues discovered during the release preparation phase are handled under the new process.

4. **CVE pre-assignment**: The current process in [SECURITY.md][SECURITY.md] states that CVE assignment begins after public disclosure. The security team should consider whether to adopt CVE pre-assignment (requesting a CVE ID during the embargo period so it can be included in the initial disclosure). This is a common practice that would benefit distributors who need to reference CVE IDs in their own advisories.
