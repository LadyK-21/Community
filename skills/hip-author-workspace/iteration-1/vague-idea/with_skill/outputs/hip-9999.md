## Abstract

This HIP proposes a declarative mechanism for Helm charts to specify cluster capability prerequisites — such as the presence of specific API groups, Custom Resource Definitions (CRDs), or required controllers — that must be satisfied before installation proceeds. A new `prerequisites` field in `Chart.yaml` allows chart authors to declare what cluster capabilities their chart depends on. During `helm install` and `helm upgrade`, Helm validates these prerequisites against the target cluster's actual capabilities (via API discovery) and fails early with a clear, actionable error message when requirements are not met.

This addresses the common pain point where charts silently deploy broken resources (e.g., Ingress objects without an ingress controller, or custom resources without their CRD installed), leading to confusing post-deployment debugging. By shifting validation left to install-time, users get immediate feedback about what their cluster is missing.

## Motivation

### Current Limitations

Today, Helm charts have no native way to declare what cluster capabilities they depend on. When a chart creates an Ingress resource but the cluster has no ingress controller, or creates a ServiceMonitor but the Prometheus Operator CRD is absent, the result is:

1. **Silent deployment of broken resources** — `helm install` succeeds, but the application does not function as expected
2. **Delayed failure signals** — users discover problems minutes or hours later when traffic fails to route or monitoring is missing
3. **Opaque error messages** — Kubernetes API errors about missing resources or unrecognized types are cryptic and do not point users toward a solution
4. **Documentation burden** — chart authors resort to lengthy README prerequisites sections that users skip or miss

### Real-World Impact

- **Chart consumers** waste significant time debugging failed deployments that could have been caught immediately. A chart depending on `cert-manager` CRDs will partially deploy and fail silently when those CRDs are absent.
- **Chart authors** receive support requests and issues that boil down to "you didn't have X installed." They cannot programmatically enforce their documented prerequisites.
- **Platform teams** managing multi-tenant clusters cannot easily validate that a chart is appropriate for their cluster's capabilities before deploying.
- **CI/CD pipelines** proceed through deployment stages only to discover at runtime that the target cluster lacks a required capability, wasting pipeline time and complicating rollback.

### Existing Workarounds

- **README documentation**: Chart authors list prerequisites in documentation, relying on users to read and follow them. This is frequently ignored.
- **Pre-install hooks with `lookup`**: Some charts use hooks that query the cluster, but this is complex, chart-specific, and provides poor UX (hook job logs are hard to surface to the user).
- **`helm template` + external validators**: Tools like `kubeval` or `kubeconform` validate rendered manifests against schemas but cannot verify that controllers or operators are actually running.
- **Wrapper scripts**: Organizations write custom scripts around `helm install` that perform prerequisite checks, fragmenting the deployment workflow.

### Who Is Affected

- **Chart consumers** (primary): anyone running `helm install` on a chart with undocumented or missed prerequisites
- **Chart authors** (secondary): those who want to provide a better install experience and reduce support burden
- **Platform operators** (tertiary): those validating chart compatibility with cluster offerings

## Rationale

### Why Declarative Prerequisites in Chart.yaml

Placing prerequisite declarations in `Chart.yaml` makes them:

- **Discoverable** — tools, registries, and `helm show chart` can surface them without rendering templates
- **Static** — they do not depend on values or template logic, making them predictable and cacheable
- **Enforceable** — Helm itself can validate them at a well-defined point in the install lifecycle (before template rendering)

This approach mirrors how `kubeVersion` already constrains the Kubernetes version. The proposal extends this pattern to cluster capabilities.

### Why Not Template-Time Checks with `lookup`

While `lookup` can query the cluster during rendering, it has significant drawbacks:

- It requires chart authors to write complex template logic for each prerequisite
- Error messages are custom per chart, inconsistent across the ecosystem
- It fails during `helm template` (no cluster context), preventing offline validation
- It mixes concerns: template logic should focus on generating manifests, not validating the environment

### Why Focus on Capabilities, Not Resource Sizing

An earlier formulation of this idea included resource sizing checks (e.g., "at least 3 nodes" or "minimum 16GB RAM available"). This was deliberately excluded because:

- Resource availability is dynamic and changes between check-time and deploy-time
- Node count and available resources are scheduling concerns better handled by Kubernetes itself (resource requests, pod anti-affinity, topology constraints)
- Including sizing would make the feature scope unbounded and implementation far more complex
- Cluster capability (API availability, CRD presence) is a stable, binary property — either the API exists or it does not

### How Other Projects Handle This

- **Ansible**: uses `meta/requirements.yml` to declare collection and role dependencies
- **Terraform**: providers declare required provider versions and features
- **apt/yum**: packages declare dependencies that must be satisfied before installation
- **OLM (Operator Lifecycle Manager)**: operators declare `required` APIs in their ClusterServiceVersion

The proposed approach aligns with these well-established dependency declaration patterns.

## Specification

### Chart.yaml Extension

A new optional `prerequisites` field is added to `Chart.yaml`:

```yaml
apiVersion: v2
name: my-application
version: 1.0.0
# ... other fields ...

prerequisites:
  capabilities:
    - apiGroup: "networking.k8s.io"
      version: "v1"
      resource: "ingresses"
      reason: "This chart creates Ingress resources for HTTP routing"
    - apiGroup: "cert-manager.io"
      version: "v1"
      resource: "certificates"
      reason: "TLS certificates are managed by cert-manager"
    - apiGroup: "monitoring.coreos.com"
      version: "v1"
      resource: "servicemonitors"
      reason: "Prometheus ServiceMonitor is used for metrics collection"
      optional: true
```

### Schema

```yaml
prerequisites:
  capabilities:
    - apiGroup: string     # Required. The API group (e.g., "networking.k8s.io", "" for core)
      version: string      # Required. The API version (e.g., "v1", "v1beta1")
      resource: string     # Required. The plural resource name (e.g., "ingresses", "certificates")
      reason: string       # Optional. Human-readable explanation displayed on failure
      optional: bool       # Optional. Default: false. If true, a warning is issued instead of an error
```

### Validation Behavior

During `helm install` and `helm upgrade`:

1. Helm reads the `prerequisites.capabilities` list from the chart metadata
2. For each capability entry, Helm queries the cluster's API discovery endpoint (`/apis` or `/api/v1` for core resources) to check if the specified `apiGroup/version/resource` triple is registered
3. **If a required capability is missing**: Helm fails immediately with a clear error message and does not proceed to template rendering
4. **If an optional capability is missing**: Helm prints a warning and continues

### Error Output

```
$ helm install my-release ./my-chart
Error: INSTALLATION FAILED: cluster prerequisites not met:
  - missing required capability: cert-manager.io/v1/certificates
    reason: TLS certificates are managed by cert-manager
    hint: install cert-manager (https://cert-manager.io/docs/installation/)
  - missing required capability: monitoring.coreos.com/v1/servicemonitors
    (marked optional - continuing with warning)

Required capabilities can be viewed with: helm show prerequisites ./my-chart
```

### CLI Additions

**`helm show prerequisites CHART`**: Displays the prerequisite declarations from a chart without installing it.

```
$ helm show prerequisites ./my-chart
CAPABILITIES:
  networking.k8s.io/v1/ingresses (required)
    This chart creates Ingress resources for HTTP routing
  cert-manager.io/v1/certificates (required)
    TLS certificates are managed by cert-manager
  monitoring.coreos.com/v1/servicemonitors (optional)
    Prometheus ServiceMonitor is used for metrics collection
```

**`--skip-prerequisites`**: A flag on `helm install` and `helm upgrade` that bypasses prerequisite validation. This is an escape hatch for advanced users who know what they are doing (e.g., installing the chart and the prerequisite concurrently).

```
$ helm install my-release ./my-chart --skip-prerequisites
WARNING: Skipping prerequisite validation. The chart declares requirements that have not been verified.
```

### Behavior Matrix

| Operation | Prerequisites Checked | Notes |
|-----------|----------------------|-------|
| `helm install` | Yes | Fails before rendering if requirements unmet |
| `helm upgrade` | Yes | Fails before rendering if requirements unmet |
| `helm install --skip-prerequisites` | No | Warning printed, proceeds |
| `helm template` | No | No cluster context available |
| `helm install --dry-run=client` | No | No cluster context available |
| `helm install --dry-run=server` | Yes | Validates against actual cluster |
| `helm show prerequisites` | N/A | Displays declared prerequisites |
| `helm lint` | No | Static check only; validates schema correctness |

### Edge Cases

- **CRD installed but controller not running**: The prerequisite check validates API registration, not controller health. This is a deliberate limitation — checking controller health would require chart-specific probes and is out of scope. The `reason` field can note this distinction.
- **Dependency charts providing the capability**: If a chart's `dependencies` include a sub-chart that installs the required CRD, the prerequisite should still be listed (CRDs from dependency charts may not be registered until after the parent chart is installed). Chart authors should use `optional: true` or omit the prerequisite in such cases.
- **Empty `prerequisites` field**: Treated as no prerequisites. Charts without the field behave identically to today.
- **Unknown fields in `prerequisites`**: Ignored with a warning, following Helm's existing forward-compatibility approach for Chart.yaml.

## Backwards Compatibility

This proposal is fully backwards compatible:

- **Additive field**: The `prerequisites` field in `Chart.yaml` is optional. Existing charts without it behave identically to today.
- **Old Helm versions**: Helm versions that do not understand `prerequisites` will silently ignore the field (Helm already ignores unknown Chart.yaml fields). Charts using this feature will still install on older Helm versions — they just will not benefit from the prerequisite validation.
- **No behavior changes**: For charts that do not declare prerequisites, the install/upgrade flow is unchanged. There are no new required flags or configuration.
- **Safe for minor version**: This is purely additive behavior gated behind an opt-in declaration, suitable for a minor Helm version release.

## Security Implications

### API Discovery Information Leakage

The prerequisite check queries the cluster's API discovery endpoints. These endpoints are already accessible to any authenticated user (they are required for `kubectl` to function). No new permissions or API access is introduced.

### Malicious Charts

A malicious chart could declare prerequisites to probe what capabilities a cluster has (by observing which prerequisites pass or fail in error messages). However:

- This information is already available to anyone who can run `helm install` (they can use `kubectl api-resources`)
- The prerequisite check happens before any resources are created, so it does not enable any new attack vectors
- The `--skip-prerequisites` flag gives users full control

### Denial of Service via Excessive Prerequisites

A chart with an extremely large `prerequisites` list could cause many API discovery requests. Mitigation: Helm should cap the number of prerequisite entries (recommended limit: 50) and batch discovery requests where possible.

### No Privilege Escalation

Prerequisite validation uses only the API discovery endpoint, which requires no elevated permissions beyond what `helm install` already needs. It does not create, modify, or delete any cluster resources.

## How to Teach This

### Documentation Additions

1. **Chart.yaml Reference**: Add `prerequisites` to the Chart.yaml specification page with full schema documentation
2. **Best Practices Guide**: "Declaring Chart Prerequisites" — when and how to use prerequisites effectively
3. **Migration Guide**: How to convert README-documented prerequisites into declarative `prerequisites` entries
4. **Helm Show**: Document `helm show prerequisites` alongside existing `helm show` subcommands

### Key Example Pattern

For a chart author adding prerequisites to an existing chart:

```yaml
# Chart.yaml
apiVersion: v2
name: my-web-app
version: 2.0.0
description: A web application with TLS and monitoring

prerequisites:
  capabilities:
    - apiGroup: "networking.k8s.io"
      version: "v1"
      resource: "ingresses"
      reason: "Required for HTTP/HTTPS routing to the application"
    - apiGroup: "cert-manager.io"
      version: "v1"
      resource: "certificates"
      reason: "Automatic TLS certificate provisioning via cert-manager"
    - apiGroup: "monitoring.coreos.com"
      version: "v1"
      resource: "servicemonitors"
      reason: "Prometheus metrics collection (application still works without this)"
      optional: true
```

### Teaching Approach

For new Helm users: "Just like `kubeVersion` tells Helm what Kubernetes version your chart needs, `prerequisites` tells Helm what cluster capabilities your chart needs. If something is missing, Helm tells you right away instead of deploying broken resources."

For experienced users: "If you have a README section listing prerequisites, you can now make those machine-readable. Add them to `prerequisites.capabilities` and Helm will validate them automatically."

## Reference Implementation

No implementation exists yet. The implementation will involve:

1. **Chart.yaml schema extension**: Add `prerequisites` to the chart metadata schema with validation
2. **API discovery integration**: Add a prerequisites checker that queries the cluster's discovery API (`/apis` and `/api/v1`) to verify capability availability
3. **Install/upgrade lifecycle hook**: Insert prerequisite validation after chart loading but before template rendering
4. **CLI additions**: `helm show prerequisites` subcommand and `--skip-prerequisites` flag
5. **Error formatting**: Clear, actionable error messages listing all unmet prerequisites
6. **Lint integration**: Validate prerequisite schema correctness in `helm lint`

## Rejected Ideas

- **Resource sizing checks (node count, memory, CPU)**: Resource availability is dynamic and ephemeral. Checking "at least 3 nodes" at install time provides a false sense of safety because nodes can disappear between the check and pod scheduling. Kubernetes already handles resource constraints through requests/limits and scheduling. Including this would make the feature scope unbounded.
- **Controller health checks**: Verifying that a controller is not just registered but actively running and healthy would require chart-specific probe logic, timeouts, and health definitions. The API group being registered is a sufficient proxy for "this capability is intended to be available." Health monitoring is the domain of the platform operator.
- **Values-conditional prerequisites**: Allowing prerequisites to be conditional on values (e.g., "only require cert-manager if `tls.enabled=true`") would require evaluating prerequisites after values merging, complicating the lifecycle. Chart authors can use `optional: true` for capabilities that are only needed in some configurations, and document the relationship.
- **Inline remediation commands**: Including install commands for missing prerequisites (e.g., `install: "helm install cert-manager jetstack/cert-manager"`) was considered but rejected because: install procedures change over time, vary by environment, and could be a security risk if executed automatically.
- **Arbitrary Lua/CEL expressions**: A general-purpose expression language for prerequisites would be extremely powerful but introduces complexity, security concerns (arbitrary code execution), and a learning curve disproportionate to the problem being solved.
- **Namespace-scoped checks**: Checking for resources in specific namespaces (e.g., "cert-manager must be in namespace cert-manager") was rejected because API group registration is cluster-scoped and sufficient. Namespace-level checks would require additional permissions and are fragile.
- **Integration with chart dependencies**: Automatically inferring prerequisites from sub-chart resources was considered but rejected because: sub-charts may install CRDs themselves (making the prerequisite circular), and explicit declaration is clearer and more maintainable.

## Open Issues

1. **Exact validation timing**: Should prerequisites be checked before or after chart dependency resolution? If a dependency chart installs the CRD that the parent chart needs, checking before dependency installation would produce a false failure. The current proposal suggests checking after dependencies are installed, but this needs further discussion.
2. **Version constraints on capabilities**: Should chart authors be able to specify minimum versions of an API (e.g., "networking.k8s.io/v1 but not v1beta1 only")? The current schema uses exact version matching. Wildcard or range support could be added later.
3. **Registry integration**: Should chart registries (Artifact Hub, OCI registries) surface prerequisite information in search results and chart pages? This is desirable but out of scope for the initial implementation.
4. **Helm SDK consumers**: How should the prerequisites check be exposed in the Helm SDK for tools like Fleet, ArgoCD, or Flux that use Helm programmatically? They may want to handle prerequisite failures differently than the CLI.
5. **`reason` field localization**: Should the `reason` field support multiple languages or link to external documentation? For now, plain English text is sufficient.
