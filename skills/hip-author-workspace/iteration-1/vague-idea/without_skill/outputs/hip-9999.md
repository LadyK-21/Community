## Abstract

This HIP proposes a declarative mechanism for Helm charts to specify cluster capability prerequisites -- requirements that the target Kubernetes cluster must satisfy before installation proceeds. Today, charts can declare a minimum Kubernetes version via `kubeVersion` in Chart.yaml, but there is no standard way to express richer requirements such as "an Ingress controller must be present," "the cluster must have a minimum number of nodes," or "a specific CRD must be installed." This proposal introduces a new `prerequisites` section in Chart.yaml that allows chart authors to declare capability, resource, and API requirements. When `helm install` or `helm upgrade` is invoked, Helm evaluates these prerequisites against the live cluster and either proceeds, emits warnings, or fails with actionable error messages, depending on the severity level declared by the chart author.

## Motivation

### Current Limitations

Helm charts frequently assume the existence of cluster capabilities that are not guaranteed:

**Ingress Controllers:** Many charts create Ingress resources, but Helm does not verify that an Ingress controller is running. The resources are created successfully (the Kubernetes API accepts them), but they have no effect. Users are left debugging why their application is unreachable.

**Custom Resource Definitions (CRDs):** Charts that depend on CRDs from other operators (e.g., cert-manager `Certificate` resources, Prometheus `ServiceMonitor` resources) fail at install time with obscure errors like `no matches for kind "Certificate" in version "cert-manager.io/v1"`. The user must independently discover, install, and configure the dependency.

**Node Capacity:** Stateful workloads like databases or distributed systems (e.g., Elasticsearch, Kafka) require minimum node counts or resource availability. Charts deploy successfully but pods remain Pending indefinitely, leaving users to diagnose scheduling failures.

**Storage Classes:** Charts requesting PersistentVolumeClaims with a specific StorageClass fail silently when that class does not exist. The PVC is created but never bound, and the dependent pods never start.

**API Versions:** The existing `kubeVersion` field checks the server version string, but does not verify whether specific API groups or versions are actually available (which depends on feature gates, API aggregation, and installed extensions).

### Who Is Affected

- **Chart consumers** waste time debugging deployment failures that could have been caught upfront.
- **Chart authors** write extensive documentation listing prerequisites, but users frequently skip or miss these sections.
- **Platform teams** managing multi-tenant clusters receive support requests for issues that are cluster-configuration problems, not chart problems.
- **CI/CD pipelines** that deploy charts fail late in the process, after potentially disruptive partial installations.

### Existing Workarounds

Chart authors currently work around these limitations using:

1. **Documentation:** Listing prerequisites in README files. This is easily missed and not machine-readable.
2. **Pre-install hooks with `lookup()`:** Running Jobs that query the cluster, but this requires RBAC privileges, adds deployment time, and the error reporting is limited (see HIP-0019 for related hook output improvements).
3. **Template-time `lookup()` calls:** Using `{{ if not (lookup "networking.k8s.io/v1" "IngressClass" "" "") }} {{ fail "..." }} {{ end }}` in templates. This works for simple API checks but cannot verify operational capabilities (e.g., "is a controller actually processing these resources?"), does not work with `helm template` or `--dry-run=client`, and scatters prerequisite logic across templates instead of centralizing it.
4. **External tools:** Tools like Troubleshoot.sh preflight checks (referenced in HIP-0019) provide this capability but require separate installation and are not part of the chart itself.

None of these approaches are standardized, composable, or provide a consistent user experience.

## Rationale

### Why Chart.yaml

Prerequisites are metadata about what a chart requires from the environment. Like `kubeVersion`, `apiVersion`, `dependencies`, and `annotations`, they belong in Chart.yaml because:

- They are declarative and can be evaluated before template rendering
- They are inspectable without installing the chart (`helm show chart`)
- They compose naturally with chart dependencies (a parent chart's prerequisites are the union of its own and its subcharts' prerequisites)
- They are machine-readable, enabling tooling beyond Helm (e.g., marketplace UIs, GitOps tools, policy engines)

### Why Not Extend `kubeVersion`

The `kubeVersion` field uses semver constraint syntax and is limited to matching the Kubernetes server version string. Extending it to cover arbitrary capabilities would be a semantic overload. Prerequisites are a different class of metadata: they describe cluster state, not just the server binary version.

### Why Not Template-Only

A template-only approach (using `lookup()` and `fail`) has been available since Helm 3 and adoption for prerequisite checking is minimal. The reasons are:

- It does not work with `helm template` or `--dry-run=client`, preventing offline validation
- It intermingles prerequisite checks with resource generation logic
- There is no standard structure, so every chart invents its own approach
- It cannot be aggregated across chart dependencies
- It provides no way to distinguish hard failures from soft warnings

### Severity Levels

The proposal includes two severity levels:

- **`required`** (default): Installation fails if the prerequisite is not met. Used for capabilities without which the chart fundamentally cannot function.
- **`recommended`**: Installation proceeds with a prominent warning. Used for capabilities that enhance the chart but are not strictly necessary (e.g., metrics collection via Prometheus).

A `required`/`recommended` distinction is deliberately simple. More granular severity levels were considered and rejected (see Rejected Ideas) to keep the mental model accessible.

### Prior Art

- **Kubernetes itself** uses feature gates and API discovery to manage capability availability.
- **Operator Lifecycle Manager (OLM)** in OpenShift has a `required` section in ClusterServiceVersion manifests for specifying API and CRD dependencies.
- **Troubleshoot.sh** provides preflight check specifications with pass/warn/fail outcomes.
- **APT/RPM package managers** have `Depends`, `Recommends`, and `Suggests` for expressing dependency strength.
- **Terraform** has `required_providers` blocks for declaring infrastructure prerequisites.

The design draws from OLM's API requirement declarations and Troubleshoot.sh's outcome model while keeping the specification chart-native and lightweight.

## Specification

### Chart.yaml Extension

A new optional `prerequisites` field is added to Chart.yaml. It contains a list of prerequisite declarations, each specifying a type, parameters, and severity.

```yaml
apiVersion: v2
name: my-application
version: 1.0.0
kubeVersion: ">=1.26.0"
prerequisites:
  # Require that the networking.k8s.io/v1 IngressClass API exists
  # (implies an Ingress controller is installed)
  - type: apiVersion
    apiVersion: "networking.k8s.io/v1"
    kind: IngressClass
    severity: required
    reason: "This chart creates Ingress resources that require an Ingress controller."

  # Require cert-manager CRDs
  - type: apiVersion
    apiVersion: "cert-manager.io/v1"
    kind: Certificate
    severity: required
    reason: "TLS certificates are managed via cert-manager. Install cert-manager before deploying this chart."

  # Recommend Prometheus Operator for monitoring
  - type: apiVersion
    apiVersion: "monitoring.coreos.com/v1"
    kind: ServiceMonitor
    severity: recommended
    reason: "ServiceMonitor resources enable automatic Prometheus scraping. Monitoring will be limited without the Prometheus Operator."

  # Require a minimum number of schedulable nodes
  - type: nodeCount
    minimum: 3
    severity: required
    reason: "This chart deploys a 3-node distributed database that requires at least 3 schedulable nodes."

  # Require a specific StorageClass
  - type: storageClass
    name: "fast-ssd"
    severity: required
    reason: "High-performance SSD storage is required for the database volumes."

  # Require minimum allocatable resources across the cluster
  - type: clusterResources
    cpu: "8"
    memory: "32Gi"
    severity: recommended
    reason: "The full deployment with all replicas requires at least 8 CPU cores and 32Gi of memory across schedulable nodes."
```

### Prerequisite Types

#### `apiVersion`

Checks whether a specific API group/version (and optionally a specific resource kind) is available via the Kubernetes API discovery mechanism.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `apiVersion` | string | yes | The API group/version to check (e.g., `networking.k8s.io/v1`, `apps/v1`) |
| `kind` | string | no | A specific resource kind within the API group/version |
| `severity` | string | no | `required` (default) or `recommended` |
| `reason` | string | no | Human-readable explanation shown when the check fails |

**Evaluation:** Uses the Kubernetes discovery API (`/apis` and `/api`) to check whether the specified group/version is registered. If `kind` is specified, further checks that the resource type exists in that group/version. This mirrors the mechanism Helm already uses internally for resource mapping.

#### `nodeCount`

Checks the number of schedulable (non-cordoned, Ready) nodes in the cluster.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `minimum` | integer | yes | Minimum number of schedulable nodes |
| `severity` | string | no | `required` (default) or `recommended` |
| `reason` | string | no | Human-readable explanation |

**Evaluation:** Lists nodes, filters to those with `Ready` condition `True` and `spec.unschedulable != true`, and compares count against `minimum`.

#### `storageClass`

Checks whether a specific StorageClass exists in the cluster.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | yes | Name of the StorageClass to check |
| `severity` | string | no | `required` (default) or `recommended` |
| `reason` | string | no | Human-readable explanation |

**Evaluation:** Attempts to get the named StorageClass from the `storage.k8s.io/v1` API.

#### `clusterResources`

Checks aggregate allocatable resources across schedulable nodes.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `cpu` | string | no | Minimum allocatable CPU (Kubernetes quantity format) |
| `memory` | string | no | Minimum allocatable memory (Kubernetes quantity format) |
| `severity` | string | no | `required` (default) or `recommended` |
| `reason` | string | no | Human-readable explanation |

**Evaluation:** Sums `status.allocatable` across schedulable nodes and compares against declared minimums. At least one of `cpu` or `memory` must be specified.

**Important caveat:** This check reports total allocatable resources, not available (unallocated) resources. Determining truly available resources would require inspecting all existing pod resource requests across the cluster, which is expensive and requires broad RBAC permissions. The allocatable check establishes whether the cluster is sized appropriately, not whether it currently has spare capacity.

### Evaluation Behavior

#### During `helm install` and `helm upgrade`

1. After chart loading and dependency resolution but before template rendering, Helm evaluates all prerequisites from the chart and its transitive dependencies.
2. Prerequisites are deduplicated: if the same check (identical type and parameters) appears multiple times, the strictest severity wins.
3. Each prerequisite is evaluated against the cluster.
4. Results are categorized:
   - **Failed required prerequisites:** Installation is aborted. All failures are reported together (not just the first) so the user can address them in one pass.
   - **Failed recommended prerequisites:** Warnings are printed to stderr. Installation proceeds.
   - **Passed prerequisites:** Reported at `--debug` verbosity.
5. Error output includes the `reason` text from the chart author, providing actionable guidance.

Example failure output:

```
Error: INSTALLATION FAILED: cluster prerequisites not met

REQUIRED (installation cannot proceed):
  [FAIL] apiVersion networking.k8s.io/v1 IngressClass: API not found
         Reason: This chart creates Ingress resources that require an Ingress controller.
  [FAIL] storageClass fast-ssd: StorageClass not found
         Reason: High-performance SSD storage is required for the database volumes.

RECOMMENDED (warnings):
  [WARN] apiVersion monitoring.coreos.com/v1 ServiceMonitor: API not found
         Reason: ServiceMonitor resources enable automatic Prometheus scraping. Monitoring will be limited without the Prometheus Operator.

2 required prerequisite(s) failed. Use --skip-prerequisites to override.
```

#### During `helm template` and `--dry-run=client`

Prerequisites are not evaluated (no cluster access). A note is printed indicating that prerequisite validation was skipped. The `prerequisites` section can still be inspected via `helm show chart`.

#### During `--dry-run=server`

Prerequisites are evaluated against the cluster, matching live install/upgrade behavior.

### Command-Line Flags

| Flag | Description |
|------|-------------|
| `--skip-prerequisites` | Skip all prerequisite checks. Installation proceeds regardless of prerequisite failures. |
| `--skip-prerequisites=recommended` | Skip only recommended prerequisite checks. Required prerequisites are still enforced. |

The `--skip-prerequisites` flag provides an escape hatch for scenarios where the user knows better than the chart (e.g., a custom Ingress controller that does not register IngressClass resources, or a cluster autoscaler that will add nodes on demand).

### New Command: `helm prerequisites`

A new subcommand allows evaluating prerequisites without installing:

```bash
# Check prerequisites for a chart against the current cluster
helm prerequisites show ./my-chart

# Check prerequisites against a specific cluster context
helm prerequisites show ./my-chart --kube-context production

# Output in JSON for tooling consumption
helm prerequisites show ./my-chart --output json
```

This enables CI/CD pipelines and platform tools to validate prerequisites independently of installation.

### Subchart and Dependency Handling

Prerequisites from subcharts and dependencies are aggregated into the parent chart's prerequisite evaluation:

1. Each dependency's prerequisites are loaded recursively.
2. Prerequisites are evaluated as a flat list after deduplication.
3. If a dependency is conditional (e.g., `condition: redis.enabled`), its prerequisites are only evaluated when the condition is true. Condition evaluation uses the merged values, consistent with how Helm resolves dependency conditions today.
4. Conflicting prerequisites (e.g., parent requires `storageClass: fast-ssd` and subchart requires `storageClass: standard`) are both evaluated independently -- both must pass.

### Schema Validation

The `prerequisites` field is validated during `helm lint` and `helm package`:

- Each entry must have a valid `type`
- Required fields for each type must be present
- `severity` must be `required` or `recommended` (defaults to `required` if omitted)
- Unknown fields generate a warning (for forward compatibility with future prerequisite types)

## Backwards Compatibility

This proposal is fully backwards compatible:

- The `prerequisites` field in Chart.yaml is optional. Existing charts work unchanged.
- Older versions of Helm that do not understand `prerequisites` will ignore the field, as Chart.yaml allows arbitrary additional fields. Charts using prerequisites will still install on older Helm versions, just without the safety checks.
- No existing Chart.yaml fields are modified or removed.
- No changes to template rendering, release storage, or any other existing behavior.
- The `--skip-prerequisites` flag ensures users are never blocked by prerequisites if they choose to override them.

The `apiVersion: v2` chart format already permits additional top-level keys in Chart.yaml without schema errors, so the addition of `prerequisites` does not require a new chart API version.

## Security Implications

### RBAC Requirements

Prerequisite evaluation requires the Helm client (or its service account) to have read access to cluster-level resources:

- **API discovery:** Already required by Helm for resource mapping. No additional permissions needed for `apiVersion` checks.
- **Node listing:** Requires `get`/`list` on `nodes` (cluster-scoped). This may not be available in restricted environments where Helm is limited to namespace-scoped operations.
- **StorageClass listing:** Requires `get` on `storageclasses.storage.k8s.io` (cluster-scoped).
- **Resource aggregation:** Requires `list` on `nodes` with access to `status.allocatable`.

If Helm lacks the permissions to evaluate a prerequisite, the check is treated as a warning (not a failure) with a message indicating that the check could not be performed due to insufficient permissions. This ensures that prerequisite checks do not break existing deployments in restricted RBAC environments.

### Information Disclosure

Prerequisite checks only read cluster state; they do not expose any information that is not already available to the Helm user via `kubectl`. The `reason` field is authored by the chart maintainer and does not contain cluster-derived data.

### Malicious Charts

A malicious chart author could declare prerequisites designed to:

- **Fingerprint cluster capabilities:** By observing which prerequisites pass or fail. Mitigation: This information is already available to chart templates via `lookup()` and `.Capabilities`. Prerequisites do not expand the information surface.
- **Cause denial of service:** By declaring an expensive prerequisite check (e.g., `clusterResources` on a very large cluster). Mitigation: All prerequisite types defined in this proposal have bounded evaluation cost. Future prerequisite types should be evaluated for cost before acceptance.

## How to Teach This

### Documentation Additions

1. **Chart.yaml Reference:** Add `prerequisites` to the Chart.yaml specification with field descriptions and type reference.
2. **Chart Developer Guide:** A new "Declaring Prerequisites" section explaining when and how to use each prerequisite type, with guidance on choosing between `required` and `recommended`.
3. **Best Practices Guide:** Add recommendations such as:
   - Always include a `reason` with actionable remediation steps
   - Prefer `apiVersion` checks over `nodeCount` or `clusterResources` when possible (API checks are cheap and deterministic)
   - Use `recommended` for capabilities that enhance but are not essential to the chart
   - Do not use prerequisites for conditions that can be handled gracefully by conditional templates

### User-Facing Messages

All prerequisite failure messages should follow a consistent format:

```
[FAIL|WARN] <type> <identifier>: <what was checked and the result>
         Reason: <chart author's explanation with remediation steps>
```

### Example: Adding Prerequisites to an Existing Chart

A chart author who maintains a web application chart with Ingress support would add:

```yaml
# Chart.yaml
prerequisites:
  - type: apiVersion
    apiVersion: "networking.k8s.io/v1"
    kind: IngressClass
    severity: recommended
    reason: >-
      An Ingress controller is needed to expose the application externally.
      Install an Ingress controller such as ingress-nginx
      (https://kubernetes.github.io/ingress-nginx/) or set
      ingress.enabled=false to use a different exposure method.
```

This is marked `recommended` rather than `required` because the chart can function without Ingress (the user might use a LoadBalancer Service or port-forward instead).

## Rejected Ideas

### Arbitrary Scripting / Custom Checks

Allowing chart authors to define custom prerequisite checks via embedded scripts (bash, Lua, Wasm, etc.) was considered. This was rejected because:

- It introduces a security risk (executing arbitrary code from a chart before the user has reviewed the rendered manifests)
- It makes prerequisites non-portable and hard to reason about
- It conflicts with Helm's declarative philosophy
- Custom checks can still be implemented via pre-install hooks (see HIP-0019 for improved hook output)

### Fine-Grained Severity Levels

A five-level severity scale (critical, required, recommended, optional, informational) was considered. This was rejected in favor of the simpler required/recommended binary because:

- Two levels cover the dominant use cases (must-have vs. nice-to-have)
- More levels require users to understand subtle distinctions that rarely affect behavior
- Additional levels can be added in a future HIP if demand materializes

### Resource-Level Prerequisites (Per-Template)

Attaching prerequisites to individual templates (e.g., "only render this Ingress if IngressClass exists") was considered. This was rejected because:

- It conflates prerequisite checking with conditional rendering, which templates already handle via `{{ if }}` and `lookup()`
- Chart-level prerequisites are simpler to reason about and aggregate across dependencies
- Template-level conditions are better expressed as values (e.g., `ingress.enabled`)

### Namespace-Scoped Checks

Checking for specific resources within a namespace (e.g., "a Secret named `tls-cert` must exist") was considered. This was rejected because:

- It overlaps with Helm's existing dependency mechanism and `lookup()` in templates
- Namespace-scoped resources are often created by the chart itself or its hooks
- It would significantly expand the prerequisite specification surface

### Operational Checks (Liveness/Health)

Checking not just that an API exists but that a controller is operational (e.g., "the Ingress controller is healthy and processing resources") was considered. This was rejected because:

- There is no standard mechanism to determine whether a controller is "operational" across all implementations
- It would require executing probes or health checks, which is slow and unreliable
- API availability (via discovery) is a good proxy for controller presence in practice

### Using Annotations Instead of a Top-Level Field

Placing prerequisites in Chart.yaml `annotations` (similar to HIP-0015 for images) was considered. This was rejected because:

- Prerequisites have structured, typed data that maps poorly to annotation string values
- Annotations are intended for metadata consumed by external tools, not by Helm itself
- A top-level field enables schema validation and clearer documentation

### Embedding in values.yaml

Placing prerequisites in values.yaml was rejected because:

- Prerequisites are chart metadata, not user-configurable values
- Users should not be able to accidentally disable safety checks by overriding values
- values.yaml is for parameterizing the chart, not declaring its environmental requirements

## Open Issues

1. **Extensibility mechanism for custom prerequisite types:** Should this proposal include a plugin or extension point for registering custom prerequisite types, or should new types only be added through future HIPs? A plugin system would be more flexible but adds complexity to the initial implementation.

2. **Interaction with `helm diff` plugins:** Popular plugins like `helm-diff` run template rendering without installing. Should they also evaluate prerequisites? This may require plugin API changes.

3. **Dependency ordering of prerequisites:** If chart A lists chart B as a dependency, and chart B has prerequisites, should chart A be able to declare that it satisfies chart B's prerequisites (e.g., chart A installs the CRDs that chart B needs)? This relates to the broader question of install-time ordering (see HIP-0025).

4. **OCI chart metadata:** When charts are stored as OCI artifacts, should prerequisites be extractable from the OCI manifest without pulling the full chart? This would enable registries and marketplace UIs to display prerequisite information.

5. **Cluster capability reporting:** Should Helm provide a `helm cluster capabilities` command that reports what prerequisites the current cluster would satisfy? This would be useful for platform teams but expands Helm's scope.
